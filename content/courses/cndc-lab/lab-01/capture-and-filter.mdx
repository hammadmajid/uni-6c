## Install

On Fedora, the capture library and the GUI are one package, and non-root capture needs the `wireshark` group:

```
sudo dnf install wireshark
sudo usermod -aG wireshark $USER
# log out and back in, then:
wireshark
```

If the interface list is empty, the group change has not taken effect yet. `tshark` (the terminal version) comes in `wireshark-cli`.

<Deeper kind="edge" title="Windows and macOS">

**Windows**: the installer from wireshark.org bundles Npcap; tick "Install Npcap" and leave "WinPcap API-compatible mode" on. The manual's mention of WinPCap is the old name.

**macOS**: the .dmg includes a ChmodBPF helper that grants your user access to the capture devices. Install it when asked, otherwise no interfaces appear.

Both are covered in the Wireshark FAQ the manual points to.

</Deeper>

## The procedure

The manual's steps 1 to 9, compressed. One trap it does not mention comes first.

<Callout type="careful" title="Your browser may refuse to send plain HTTP">
Firefox with HTTPS-Only mode and Chrome with "Always use secure connections" silently upgrade `http://` to `https://`. Then your capture shows TLSv1.3 rows and **no HTTP at all**. Type the address with `http://` explicitly; if the browser still upgrades, allow the exception for gaia.cs.umass.edu, or generate the request from a terminal instead: `curl http://gaia.cs.umass.edu/wireshark-labs/INTRO-wireshark-file1.html`. The capture is identical either way.
</Callout>

1. Start the browser, then start Wireshark.
2. Pick the interface that carries your traffic: the one showing your LAN address, with the activity graph moving. Double-click it. Capture begins.
3. In the browser, load `http://gaia.cs.umass.edu/wireshark-labs/INTRO-wireshark-file1.html`. It is one line of congratulations, 81 bytes.
4. Stop the capture: the red square, or Capture › Stop.
5. Type `http` in the display filter and apply.
6. Click the row whose Info column begins with `GET /wireshark-labs/`.
7. In the details pane, collapse Frame, Ethernet, IP and TCP; expand Hypertext Transfer Protocol.

## Display filters

Five tasks on the lab capture. The filter is checked live: the moment the list shows exactly the right packets, the task is marked solved, whichever expression you used to get there.

<FilterLab id="filter-lab" />

<Callout type="pitfall" title="Display filter is not capture filter">
There are two filter languages, and confusing them is the classic first-week mistake. A **display filter** (`tcp.port == 80`) hides rows from a capture that still holds everything; clear it and the packets come back. A **capture filter** (`port 80`, BPF syntax, set on the interface before you start) throws away non-matching frames at the library, permanently. The manual uses only display filters. Note the different syntax: `tcp.port == 80` on one side, `tcp port 80` on the other.
</Callout>

<Deeper kind="beyond" title="The same lab from a terminal">

Everything the GUI does, `tshark` does in a pipe. Capture 30 seconds of port-80 traffic and print the HTTP rows with their relative times:

```
tshark -i wlp0s20f3 -a duration:30 -f "port 80" -Y http \
  -T fields -e frame.number -e frame.time_relative -e http.request.method -e http.response.code
```

Note the two filters: `-f` is the capture filter (BPF), `-Y` is the display filter. Question 2 of the lab is one subtraction on that output. On a VPS with no GUI, `tcpdump -w` to a file and open it in Wireshark at home; the pane layout is the same and the timestamps survive.

</Deeper>
