You have written plenty of network applications: a frontend calling an API, an API calling Postgres, a worker pulling from Redis. This week gives names to what you were already doing, starting from the top of the stack, which is where Kurose starts too.

**The port.** The IP address gets the datagram to the right machine. The machine runs dozens of processes, so the transport header carries a 16-bit port number that picks one: 443 for Nginx, 5432 for Postgres, 22 for sshd. A process is addressed by **IP address + port number**, and the thing that address points at is a **socket**.

</Predict>

## Where application code runs

Network applications run **only on end systems**. Routers and switches in the core go up to the network layer at most; they never run your code. That is why you can ship a new protocol by deploying to two machines, without asking any ISP for anything, and it is why the Web, BitTorrent and WhatsApp spread as fast as they did.

<SocketDoor />

<Callout type="key-idea" title="The socket is the API between the app and the network">
A **socket** is the interface between the application layer and the transport layer inside one host. The slides call it a door: the process pushes a message out through the door and relies on the transport infrastructure on the other side to deliver it to the door of the receiving process. Above the door the developer controls everything; below it, the developer can only choose the transport protocol and a few parameters such as buffer sizes.
</Callout>

## Two architectures

<AppArchitectures />

| | Client-server | Peer-to-peer |
|---|---|---|

| Examples | Web, email, your SaaS | BitTorrent, early Skype |

## Processes, clients and servers

Programs do not talk; **processes** do. Two processes on the same host use inter-process communication provided by the OS (pipes, Unix sockets). Processes on different hosts exchange **messages** across the network. In every communication session one side is labelled:

- **client process**: the one that **initiates** contact.
- **server process**: the one that **waits** to be contacted.

The labels are per session, not per machine. In P2P, the peer downloading a chunk is the client and the peer uploading it is the server, and a moment later they may swap.

## What an application-layer protocol defines

1. **Types of messages** exchanged: request and response.
2. **Syntax**: which fields a message has and how they are delimited.
3. **Semantics**: what the information in each field means.
4. **Rules** for when and how a process sends messages and responds to them.

Some protocols are **open**, defined in RFCs so anyone can interoperate (HTTP, SMTP, DNS). Others are **proprietary** (Zoom, the original Skype). A web application such as Gmail is not a protocol; it uses one (HTTP) as a single piece of a larger system.

## What transport service does an app need?

An app picks its transport by weighing four things:

| Application | Data loss | Throughput | Time-sensitive |
|---|---|---|---|
| File transfer, email, web documents | No loss | Elastic | No |
| Real-time audio and video | Loss-tolerant | Audio 5 kbps to 1 Mbps, video 10 kbps to 5 Mbps | Yes, 100s of ms |
| Streaming stored video | Loss-tolerant | Same as above | Yes, a few seconds |
| Interactive games | Loss-tolerant | Few kbps and up | Yes, 100s of ms |
| Text messaging | No loss | Elastic | Yes and no |

The fourth dimension is **security**: encryption, data integrity, end-point authentication. **Elastic** means the app uses whatever throughput it gets; a file download is just slower on a slow link.

## What the Internet actually offers: TCP and UDP

| | TCP | UDP |
|---|---|---|
| Connection | Connection-oriented: handshake before data | Connectionless: just send |
| Reliability | Reliable, in-order byte stream | Unreliable: loss and reordering possible |
| Flow control | Yes: sender will not overwhelm the receiver | No |
| Congestion control | Yes: throttles the sender when the network is overloaded | No |
| Timing, throughput guarantee | No | No |
| Security | No, unless TLS is added on top | No |

Neither protocol offers timing or throughput guarantees; applications cope by design (buffering, adaptive bitrate). So why use UDP at all? It has no handshake delay, no congestion control deciding your sending rate, a smaller header, and it lets the application build exactly the reliability it wants on top. QUIC, which carries HTTP/3, is exactly that: TCP-like reliability plus TLS, rebuilt in user space over UDP.

| Application | App-layer protocol | Transport |
|---|---|---|
| Email | SMTP (RFC 5321) | TCP |
| Remote terminal | Telnet, today SSH | TCP |
| Web | HTTP/1.1 and HTTP/2, HTTP/3 (RFC 9110 to 9114) | TCP; UDP for HTTP/3 |
| File transfer | FTP (RFC 959) | TCP |
| Streaming | HTTP (DASH) | TCP |
| Internet telephony | SIP, RTP, proprietary | Usually UDP |

The slides call it **SSL** (Secure Sockets Layer) and say it gives an encrypted TCP connection, data integrity and end-point authentication, implemented as a library at the application layer. All true of its successor. SSL itself was retired years ago (SSL 3.0 was formally deprecated in 2015); what your Nginx speaks is **TLS** 1.2 or 1.3. <Deeper kind="beyond" title="The P2P numbers: why BitTorrent beats a server for big files">

Kurose gives a distribution-time bound. A file of F bits goes to N peers. The server uploads at `u_s`, each peer uploads at `u`, and the slowest peer downloads at `d_min`.

- **Client-server**: the server must push N copies, so `D_cs ≥ max(N·F / u_s, F / d_min)`. It grows **linearly** in N.
- **P2P**: the server pushes at least one copy, and total upload capacity grows with N: `D_p2p ≥ max(F / u_s, F / d_min, N·F / (u_s + N·u))`. As N grows, the last term levels off at F / u, so the time **flattens**.

With F = 1 GB (8 × 10⁹ bits), `u_s` = 100 Mbps, `u` = 5 Mbps, fast downloaders and 1000 peers: client-server needs at least 80,000 s (22 hours); P2P needs about 8 × 10¹² ÷ 5.1 × 10⁹ ≈ 1,570 s (26 minutes). This is why Linux ISOs are distributed by torrent.

</Deeper>

<Deeper kind="exam" title="Model answer: compare client-server and P2P architectures (5 marks)">

Define both in one sentence each. **Client-server**: an always-on server host with a fixed, well-known IP address serves requests from clients, which do not communicate with each other directly; large services use data centers to scale. **P2P**: minimal or no reliance on always-on servers; intermittently connected peers with changing IP addresses communicate directly, each both requesting and providing service.

Then contrast three points: scalability (P2P is self-scalable, client-server needs more infrastructure); management (P2P is harder: peers leave, addresses change, security and incentives are hard); cost (client-server pays for servers and bandwidth, P2P spreads cost to peers). Examples: the Web and email for client-server, BitTorrent for P2P.

</Deeper>
