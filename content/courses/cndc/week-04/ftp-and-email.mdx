Two of the oldest application protocols still examined everywhere. FTP is interesting for how it uses connections; email for how three protocols divide one job.

## FTP: the file transfer protocol

FTP (RFC 959) moves files between a local host and a remote one. The client is the side that initiates, whichever direction the file goes. The user logs in with a user name and password, browses the remote directory tree, and gets or puts files.

<FtpConnections />

- The client contacts the server on **TCP port 21** and opens the **control connection**. User name, password, directory changes and transfer commands all go over it, as ASCII text.
- When the server receives a transfer command, it opens a **second TCP connection**, the **data connection**, to the client (from port 20), sends exactly one file, and closes it. The next file gets a new data connection.
- The control connection stays open for the whole session. Because control travels on a different connection from the data, FTP sends its control information **out-of-band**. HTTP sends headers and body on the same connection: **in-band**.
- The server keeps **state** for the session: the logged-in user and the current directory. HTTP keeps none.

| Command | Does |
|---|---|
| `USER username` | Send user name |
| `PASS password` | Send password (in cleartext) |
| `LIST` | List files in the current remote directory, over a data connection |
| `RETR filename` | Retrieve (get) a file |
| `STOR filename` | Store (put) a file on the remote host |

Replies are a status code and a phrase, like HTTP: `331 Username OK, password required`, `125 Data connection already open; transfer starting`, `425 Can't open data connection`, `452 Error writing file`.

<Callout type="exam" title="Port 20 is only half the story">
The slide says the data connection is 'server port 20'. That is **active mode**: the server connects out to the client. Behind NAT or a firewall that connection is usually blocked, so almost every client today uses **passive mode**: the client opens the data connection to a port the server picks, not port 20. For the exam, write port 21 for control and port 20 for data, as the slides do. In practice you move files to your VPS with `scp`, `rsync` or `sftp`, all over SSH, because FTP sends your password in cleartext.

## Electronic mail

Three major components: **user agents** (Outlook, Thunderbird, the iPhone Mail app: compose, read, reply), **mail servers** (each user has a **mailbox** there; each server also keeps an outgoing **message queue**), and **SMTP**, the protocol mail servers use to send mail to each other.

<MailPath />

The slides' scenario, one step at a time:

1. Alice uses her user agent to compose a message to `bob@someschool.edu`.
2. Her user agent sends the message to her mail server, where it is placed in the message queue.
3. The client side of SMTP on Alice's server opens a TCP connection to Bob's mail server.
4. The SMTP client sends Alice's message over that connection.
5. Bob's mail server places the message in Bob's mailbox.
6. Bob invokes his user agent to read it.

On step 3, Alice's server is the SMTP **client** and Bob's server is the SMTP **server**. The same machine plays the server role when receiving mail for Alice. SMTP transfers **directly** from the sending server to the receiving server, never via an intermediate mail server, and if Bob's server is down, the message waits in the queue and is retried, typically every 30 minutes.

## SMTP up close

SMTP (RFC 5321) uses **TCP port 25** and has three phases: **handshaking** (greeting), **transfer of messages**, and **closure**. Like HTTP and FTP it is a command/response protocol: commands in ASCII text, responses as a status code and phrase. Here is Kurose's transcript, `C:` for the client (the sending server) and `S:` for the server:

```
S: 220 hamburger.edu
C: HELO crepes.fr
S: 250 Hello crepes.fr, pleased to meet you
C: MAIL FROM: <alice@crepes.fr>
S: 250 alice@crepes.fr ... Sender ok
C: RCPT TO: <bob@hamburger.edu>
S: 250 bob@hamburger.edu ... Recipient ok
C: DATA
S: 354 Enter mail, end with "." on a line by itself
C: Do you like ketchup?
C: How about pickles?
C: .
S: 250 Message accepted for delivery
C: QUIT
S: 221 hamburger.edu closing connection
```

| | HTTP | SMTP |
|---|---|---|
| Direction | **Pull**: the client asks for what it wants | **Push**: the sending server pushes to the receiving server |
| Encoding | Any bytes in the body | Whole message, body included, in **7-bit ASCII** |
| Objects | One object per response | All objects (text, images) in one multipart message |
| Connection | Persistent (1.1 onward) | Persistent |
| Style | ASCII commands, status codes | ASCII commands, status codes |

A **mail message** (RFC 822, today RFC 5322) is a **header** (lines such as `To:`, `From:`, `Subject:`), a **blank line**, then the **body**. These header lines are part of the message itself. They are not the SMTP commands `MAIL FROM` and `RCPT TO`, which address the envelope.

<Callout type="exam" title="The 7-bit ASCII rule">
The slide says SMTP messages 'must be in 7-bit ASCII'. That is the rule of the original protocol, and the right exam answer. It is why attachments are **encoded** (MIME, usually base64) into ASCII before sending, and base64 makes a file about 33% bigger. Modern servers negotiate an 8BITMIME extension, but the encoding convention stuck. Also, the slides cite obsolete RFCs: SMTP is RFC 5321 (not 2821), IMAP is RFC 9051 (not 1730), and the message format is RFC 5322 (not 822).
</Callout>

## Mail access protocols

SMTP delivers to and stores in the receiver's server. A **mail access protocol** retrieves from it.

| | POP3 (RFC 1939) | IMAP (RFC 9051) | HTTP |
|---|---|---|---|
| Model | Authorize, download, usually delete from server | Messages stay on the server; client manipulates them there | Webmail in the browser |
| Folders | Local only | Kept on the server | On the server |
| Several devices | Poor: the phone downloads and deletes, the laptop never sees it | Good: every device sees the same folders and read state | Good |
| Server state across sessions | None | Folder structure, flags | Everything |
| Examples | Old desktop clients | Thunderbird, the iPhone Mail app | Gmail, Outlook.com |

<Deeper kind="beyond" title="Sending mail from your own VPS">

Most VPS providers block outbound port 25, because spam. User agents submit mail on **port 587** with authentication; port 25 is for server-to-server relay. Even with 25 open, receiving servers check three DNS records before trusting you: **SPF** (which IPs may send for your domain), **DKIM** (a signature on each message, public key in DNS), and **DMARC** (what to do when those fail). That is why most people send application mail through a relay service. All three are DNS TXT records, which the DNS lesson explains.

</Deeper>
