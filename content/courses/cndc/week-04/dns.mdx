## What DNS does

Hosts have two identifiers: names people can remember (`gaia.cs.umass.edu`) and 32-bit IP addresses routers can use (`128.119.245.12`). DNS maps between them. It is two things at once: a **distributed database** implemented in a hierarchy of name servers, and an **application-layer protocol** that hosts and name servers use to query it, usually over **UDP port 53**.

| Service | What it means | Record |
|---|---|---|
| Name to address | The main job | A (AAAA for IPv6) |
| Host aliasing | `www.example.com` is an alias; the **canonical** name may be something ugly like `lb-7.eu-west.example.net` | CNAME |
| Mail server aliasing | Mail to `@example.com` goes to whichever host the domain names as its mail server | MX |
| Load distribution | A busy site lists several addresses; DNS rotates their order in each reply, spreading clients across replicas | several A |

DNS is a core Internet function built as an application at the edge, exactly like the apps in the previous lessons. Users rarely touch it directly; other applications (browsers, mail servers, `ssh`) call it first, and its delay adds to theirs.

## The hierarchy

<DnsHierarchy />

- **Root servers**: 13 named root servers (a to m), operated by 12 organisations and replicated as well over a thousand anycast instances worldwide. They return the addresses of TLD servers.
- **Top-level domain (TLD) servers**: one set per TLD: `.com`, `.org`, `.edu`, and country codes like `.pk`, `.uk`. Verisign runs `.com`; PKNIC runs `.pk`.
- **Authoritative servers**: every organisation with public hosts must have one (its own, or a provider's such as Cloudflare or Route 53). It holds the records for that organisation's names.
- **Local DNS server**: not strictly part of the hierarchy. Every ISP, university or public service (1.1.1.1, 8.8.8.8) runs one. It is the server your laptop is configured to ask, and it does the walking and caching on your behalf.

## Walking it: iterative and recursive

<DnsWalk />

The first query, from your laptop to the local server, is **recursive**: 'get me the final answer'. The rest are, in practice, **iterative**: each server replies either with the answer or with a **referral**, 'I don't know, but ask this server next', and the local server does the next step itself. In a fully **recursive** chain, each server would forward the query and hold it open until the answer came back up, which puts all the load and state on the servers at the top of the tree.

## Caching is what makes it fast

Every server caches every reply it receives, for the **TTL** the record carries. TLD addresses are usually cached for two days, so real lookups almost never reach a root. Popular names like `google.com` sit in your ISP's resolver permanently. The cost: a changed record keeps its old value until caches expire. That is why you lower the TTL a day before moving a site to a new VPS.

`dig +trace` makes your own machine act as the local server and do the iterative walk, printing each referral. Trimmed and simplified, with times and some server names varying per run:

```
$ dig +trace gaia.cs.umass.edu
.                   518400  IN  NS  a.root-servers.net.
edu.                172800  IN  NS  a.edu-servers.net.
;; from a.root-servers.net in 16 ms
umass.edu.          172800  IN  NS  ns1.umass.edu.
;; from a.edu-servers.net in 20 ms
gaia.cs.umass.edu.  3600    IN  A   128.119.245.12
;; from ns1.umass.edu in 221 ms
```

## Resource records

The database stores **resource records**: (Name, Value, Type, TTL).

| Type | Name | Value | Example |
|---|---|---|---|
| A | a host name | its IPv4 address | `gaia.cs.umass.edu  A  128.119.245.12` |
| NS | a domain | the host name of an authoritative server for it | `umass.edu  NS  ns1.umass.edu` |
| CNAME | an alias | the canonical name | `www.example.com  CNAME  example.netlify.app` |
| MX | a domain | the canonical name of its mail server | `example.com  MX  mail.example.com` |

When you point a domain at your VPS, you are adding these in your registrar's panel: an A record for the apex, a CNAME for `www`, and MX records if you use a mail provider. And NS records at the registrar are how the `.com` TLD servers learn which authoritative servers to refer people to.

<Deeper kind="beyond" title="The protocol, and why it is attacked">

A DNS message has the same format for queries and replies: a 12-byte header (a 16-bit ID that matches replies to queries, and flags such as 'recursion desired'), then question, answer, authority and additional sections. It is usually a single UDP datagram each way, with no handshake, which is why DNS is fast, and TCP is used for large answers and zone transfers.

UDP and caching are also why DNS gets attacked. Floods against root servers (2002, 2015) mostly failed because of anycast and caching; the 2016 attack on Dyn, an authoritative provider, took down Twitter and GitHub for hours. **Cache poisoning** tricks a resolver into caching a forged reply, which is what DNSSEC signs against. **DNS over HTTPS** (DoH) hides your queries from the network by sending them to the resolver inside TLS.

</Deeper>
