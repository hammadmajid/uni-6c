HTTP is the protocol you know best, from `curl -v` and the browser's Network tab. This lesson is about the part that gets examined: **how many round trips a page costs**, and how each version of HTTP cut that number down.

## The web in three sentences

A **web page** is a base HTML file plus the **objects** it references: images, scripts, stylesheets, video. Each object is addressable by a **URL**: `www.someschool.edu/someDept/pic.gif` is a **host name** (`www.someschool.edu`) plus a **path name** (`/someDept/pic.gif`). HTTP is the protocol a browser (client) and a web server use to request and send those objects.

<Callout type="key-idea" title="HTTP runs over TCP and is stateless">
The client opens a TCP connection to the server on port 80 (443 for HTTPS), the two exchange HTTP messages, and the connection closes. The server keeps **no information about past requests**: ask for the same object twice and it sends it twice. That is a design decision, not an oversight. A stateless server is simpler and survives crashes: nothing to recover, nothing to get out of sync. It is also why your API behind a load balancer can scale out horizontally.
</Callout>

<Callout type="exam" title="The formula">
**Response time for one object, non-persistent = 2 RTT + file transmission time.** One RTT to set up the TCP connection, one RTT for the request and the first bytes of the response, plus L/R to push the file out. For a page with M referenced objects fetched serially: (M + 1) × (2 RTT + t).
</Callout>

## Persistent HTTP

Non-persistent HTTP has three costs: **2 RTTs per object**, **OS overhead** for every TCP connection (buffers and variables allocated in client and server), and so browsers open **parallel connections** to hide the first cost, which multiplies the second.

**Persistent HTTP** (the default since HTTP/1.1): the server leaves the connection open after sending a response, and later requests between the same client and server use it.

- **Without pipelining**: the client sends the next request only after the previous response arrives. One RTT per referenced object, but no more handshakes: 2 RTT + M × RTT.
- **With pipelining**: the client sends requests as soon as it finds references, back to back. As little as **one RTT for all the referenced objects**: 3 RTT in total.

The slide's persistent-HTTP bullet says 'as little as one RTT for all the referenced objects'. That is only true **with pipelining**. ## What the messages look like

HTTP/1.1 messages are ASCII text. Here is the Lab 01 exchange, printed the way `curl -v` prints it: lines starting `>` were sent by Firefox, lines starting `<` came back from gaia.

```
* Connected to gaia.cs.umass.edu (128.119.245.12) port 80
> GET /wireshark-labs/INTRO-wireshark-file1.html HTTP/1.1
> Host: gaia.cs.umass.edu
> User-Agent: Mozilla/5.0 (X11; Linux x86_64; rv:143.0) Gecko/20100101 Firefox/143.0
> Accept-Encoding: gzip, deflate
> Connection: keep-alive
>
< HTTP/1.1 200 OK
< Date: Thu, 17 Sep 2026 07:56:46 GMT
< Server: Apache/2.4.62 (AlmaLinux) OpenSSL/3.5.5
< Last-Modified: Tue, 28 Oct 2025 05:59:01 GMT
< ETag: "51-64231b6715777"
< Content-Length: 81
< Keep-Alive: timeout=5, max=100
< Connection: Keep-Alive
< Content-Type: text/html; charset=UTF-8
<
<html>
Congratulations!  You've downloaded the first Wireshark lab file!
</html>
```

Two headers are this lesson in miniature. `Connection: keep-alive` asks for a **persistent** connection, and `Keep-Alive: timeout=5` is Apache agreeing to hold it open for 5 idle seconds. That is why the capture shows the server's FIN at 7.60 s, exactly 5 s after the 200 OK.

A **request** is a request line (method, path, version), header lines, a blank line, and an optional body (used by POST). A **response** is a status line (version, status code, phrase), header lines, a blank line, and the object.

| Code | Phrase | Meaning |
|---|---|---|
| 200 | OK | Success; the object is in the body |
| 301 | Moved Permanently | Object moved; new URL in the Location header |
| 304 | Not Modified | Your cached copy is still good (next lesson) |
| 400 | Bad Request | The server could not parse the request |
| 404 | Not Found | No such object on this server |
| 505 | HTTP Version Not Supported | The server does not speak that version |

Methods: **GET** (fetch; form input can ride in the URL after `?`), **POST** (input in the body), **HEAD** (headers only, no body; useful for debugging and link checkers), **PUT** (upload or replace the object at the URL), **DELETE**.

<Deeper kind="beyond" title="HTTP/2 and HTTP/3: pipelining done properly">

Browsers never shipped HTTP/1.1 pipelining, because one slow response blocked everything behind it (**head-of-line blocking**). They opened 6 parallel connections per host instead. **HTTP/2** (2015) sends many requests and responses interleaved as frames over one TCP connection, which is what pipelining was trying to be. It still suffers head-of-line blocking inside TCP: one lost segment stalls every stream. **HTTP/3** moves to **QUIC** over UDP, where each stream is recovered independently and the TCP and TLS handshakes are merged into one RTT. Check what your own site speaks with `curl -sI --http3 https://yoursite` (needs a curl built with HTTP/3), or look at the Protocol column in the browser's Network tab.

</Deeper>

<Deeper kind="exam" title="Model answer: non-persistent vs persistent HTTP (5 marks)">

**Non-persistent**: each TCP connection carries at most one object and is then closed. Response time per object = 2 RTT + transmission time (1 RTT for the handshake, 1 RTT for the request and the start of the response). Drawbacks: 2 RTT per object, OS overhead per connection; browsers compensate with parallel connections.

**Persistent**: the server leaves the connection open after responding; subsequent requests between the same client and server use it. Without pipelining, one RTT per referenced object; with pipelining, requests are sent back to back, so as little as one RTT for all referenced objects. Default in HTTP/1.1.

Close with a number: base file + 10 objects, RTT 100 ms, negligible transmission: non-persistent serial 2200 ms, persistent with pipelining 300 ms.

</Deeper>
