## Long answers

<Predict
  id="cp4-http-compare"
  prompt="Differentiate non-persistent and persistent HTTP. Give the response time for each when a base file references 10 objects and transmission time is negligible. (5 marks)"
  answer="Non-persistent: one object per TCP connection, 2 RTT per object, OS overhead per connection; 22 RTT serially. Persistent: server leaves the connection open; without pipelining 2 + 10 = 12 RTT, with pipelining 3 RTT."
>

**Non-persistent HTTP**: at most one object is sent over a TCP connection, which is then closed. Each object costs one RTT to set up the connection and one RTT for the request and the start of the response, plus its transmission time: **2 RTT + t**. The OS allocates buffers for every connection. Base file + 10 objects serially: 11 × 2 RTT = **22 RTT**. Browsers open parallel connections to reduce this.

**Persistent HTTP** (the HTTP/1.1 default): the server leaves the connection open after responding, and later requests and responses between the same client and server use it. Without pipelining: 2 RTT for the base file, then 1 RTT per object = **12 RTT**. With pipelining, the client sends requests back to back as it finds references: **3 RTT** in total.

</Predict>

<Predict
  id="cp4-dns-long"
  prompt="Why is DNS distributed? Describe its hierarchy and show how a host resolves a name, distinguishing iterative from recursive queries. (6 marks)"
  answer="Centralized DNS fails on single point of failure, traffic volume, distance, maintenance. Root, TLD and authoritative servers plus a local DNS server. Host sends a recursive query to the local server; the local server iterates through root, TLD and authoritative; 8 messages; caching with TTL."
>

**Why distributed**: a single server would be a single point of failure, could not handle the traffic volume, would be distant from most clients, and would be impossible to maintain. It does not scale.

**Hierarchy**: **root** servers know the TLD servers; **TLD** servers (com, org, edu, pk) know the authoritative servers for domains under them; **authoritative** servers hold an organisation's records. Each host also uses a **local DNS server** (its ISP's or a public one) that acts as a proxy into the hierarchy.

**Resolution** (draw it and number the arrows): 1 host → local (**recursive**: 'find me the answer'); 2–3 local → root → referral to the TLD; 4–5 local → TLD → referral to the authoritative server; 6–7 local → authoritative → A record; 8 local → host. Messages 2 to 7 are **iterative**: each server returns a referral and the local server does the next step. In fully recursive resolution, each server would query the next itself and hold the request until the answer came back. **Caching**: every server caches replies for the record's TTL, so most lookups skip the root.

</Predict>

<Predict
  id="cp4-email-long"
  prompt="Describe the three major components of Internet email and trace a message from Alice to Bob. Why is SMTP not used by Bob to read his mail? (5 marks)"
  answer="User agents, mail servers (mailboxes and message queue), SMTP. Alice's UA to her server's queue; SMTP client on her server opens TCP to Bob's server on port 25, pushes the message; Bob's server puts it in his mailbox; Bob's UA retrieves it with POP3, IMAP or HTTP. SMTP is push-only."
>

**Components**: **user agents** (compose, edit and read messages: Outlook, Thunderbird); **mail servers** (a mailbox per user for incoming mail, and a message queue of outgoing mail); **SMTP** (the protocol between mail servers; TCP port 25; handshaking, transfer, closure; ASCII commands, status-code replies; 7-bit ASCII messages).

**Trace**: (1) Alice composes a message to Bob in her UA; (2) the UA sends it to her mail server, which queues it; (3) the SMTP client side of her server opens a TCP connection to Bob's mail server; (4) it sends the message after the handshake; (5) Bob's server places it in his mailbox; (6) Bob reads it with his UA.

**Why not SMTP for reading**: SMTP is a **push** protocol; it transfers mail toward a server and has no command to fetch a mailbox. Bob's UA uses a mail access protocol to pull: POP3 (download, often delete), IMAP (manage mail on the server), or HTTP (webmail).

</Predict>

<Predict
  id="cp4-transport-long"
  prompt="What transport services can an application need? Compare the services TCP and UDP provide, and give one reason an application would choose UDP. (5 marks)"
  answer="Data integrity (reliability), throughput, timing, security. TCP: reliable, flow control, congestion control, connection-oriented; no timing, throughput or security guarantees. UDP: unreliable, none of those. Choose UDP to avoid handshake delay and congestion-control throttling for loss-tolerant, time-sensitive apps."
>

**Needs**: **data integrity** (file transfer and web need 100% reliable transfer; audio tolerates loss); **throughput** (multimedia needs a minimum rate; elastic apps use whatever they get); **timing** (telephony and games need low delay); **security** (encryption, integrity, authentication).

**TCP**: connection-oriented (handshake before data), reliable in-order transport, flow control, congestion control. **UDP**: unreliable connectionless data transfer; no reliability, flow control, congestion control or connection setup. **Neither** guarantees timing, minimum throughput or security; security is added with SSL/TLS at the application layer.

**Why UDP**: no connection setup delay, no congestion control deciding the sending rate, and a smaller header, so a loss-tolerant, time-sensitive application (voice, games, DNS) can send immediately and handle loss itself.

</Predict>

<Predict
  id="cp4-ftp-long"
  prompt="Explain FTP's use of two connections. What does 'out-of-band' mean here, and how does FTP differ from HTTP in state? (4 marks)"
  answer="Control connection on TCP 21 for the whole session carries USER, PASS, LIST, RETR, STOR; a new data connection (port 20) per file, closed after it. Control is separate from data, hence out-of-band; HTTP is in-band. FTP server keeps user and directory state; HTTP is stateless."
>

The client opens a **control connection** to the server on **TCP port 21**, logs in (USER, PASS) and sends commands (LIST, RETR, STOR) in ASCII over it; it stays open for the session. For each file transfer, the server opens a separate **data connection** (from port 20), sends one file and closes it. Because control information travels on a different connection from the data, FTP is **out-of-band**; HTTP sends headers and data on one connection, **in-band**. The FTP server maintains **state** (the user's identity and current directory) for the session; HTTP servers are **stateless**.

</Predict>

<Predict
  id="cp4-sockets-long"
  prompt="Explain the difference between UDP and TCP socket programming, using the uppercase client-server example. (4 marks)"
  answer="UDP: no connection, the client attaches the server address to every sendto, the server gets the client's address from each recvfrom, one server socket for all clients, data may be lost. TCP: server creates a welcoming socket, the client connects (handshake), accept returns a new connection socket per client, reliable byte stream, no address on send."
>

**UDP**: no handshake. The client creates a `SOCK_DGRAM` socket and attaches the server's IP and port to **every** `sendto`; the server, bound to port 12000, gets each datagram with the sender's address from `recvfrom` and replies to that address. One server socket serves all clients. Datagrams may be lost or reordered.

**TCP**: the server must be running first, with a **welcoming socket** (`bind`, `listen`). The client creates a `SOCK_STREAM` socket and calls `connect`, which runs the handshake. The server's `accept` returns a **new connection socket** dedicated to that client, and the two exchange data with `send` and `recv`, no addresses needed. Reliable, in-order byte stream. Many clients are handled with one connection socket each, told apart by the 4-tuple.

</Predict>
