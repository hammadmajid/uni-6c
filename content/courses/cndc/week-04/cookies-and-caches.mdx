The last lesson said HTTP is stateless. Your shopping cart disagrees. This short lesson covers the two things Kurose adds on top of plain HTTP: **cookies**, which give a stateless protocol memory, and **web caches**, which stop the same bytes crossing the same slow link twice.

**Split in two.** The shop's back-end database holds the cart, keyed by an ID number it made up on your first visit. Your browser holds only that ID, in its cookie file, and attaches it to every request to that site in a `Cookie:` header. HTTP itself stays stateless. The state lives at the two ends, and a small header ties them together.

## Cookies: four components

1. A **Set-Cookie** header line in an HTTP **response**.
2. A **Cookie** header line in later HTTP **requests**.
3. A **cookie file** on the user's host, managed by the browser.
4. A **back-end database** at the website.

This is exactly the session middleware you have configured: a `Set-Cookie: sid=...; HttpOnly; Secure` on login and a Redis or Postgres table keyed by `sid`. Cookies are how sites keep login sessions, shopping carts and recommendations, and, with **third-party cookies** set by an ad network embedded on many sites, how you get tracked across sites.

## Web caches

A **web cache** (or **proxy server**) answers HTTP requests on behalf of an origin server. The browser is configured to send every request to the cache. On a hit, the cache answers from its own copy; on a miss, it fetches the object from the origin, keeps a copy, and answers. The cache is a server to the browser and a client to the origin at the same time.

Why bother? The cache usually sits inside the institution, so a hit is fast (LAN speed, not Internet round trips) and it takes load off the **access link**, the institution's paid-for pipe to its ISP.

    An institution's LAN runs at 100 Mbps and its access link at 15 Mbps. Browsers request 15 objects per second, each 1 Mbit on average. Round trip from the access router to origin servers: 2 s.
  </Step>
  <Step label="Intensity on the access link, no cache" tryFirst="Traffic intensity is arrival rate of bits divided by link rate.">
    15 requests/s × 1 Mbit = 15 Mbps of traffic onto a 15 Mbps link. Intensity = **1.0**. From week 2: as La/R approaches 1, queueing delay grows without bound. Response times climb to minutes.
  </Step>
  <Step label="Option A: buy a 100 Mbps access link">
    Intensity drops to 0.15. Response time ≈ 2 s. Works, but the institution pays for a much bigger link every month.
  </Step>
  <Step label="Option B: install a cache with a 40% hit rate" tryFirst="What intensity does the access link see now?">
    Only 60% of requests cross the access link: 0.6 × 15 Mbps = 9 Mbps, so intensity = **0.6**. Queueing delay on the link becomes small, tens of milliseconds. Average response ≈ 0.4 × (a few ms, from the LAN) + 0.6 × (about 2.01 s) ≈ **1.2 s**, faster than option A, on the old link.
  </Step>
</WorkedExample>

## Conditional GET: is my copy still fresh?

A cache's copy may be stale. HTTP lets the cache check cheaply: it adds an **If-Modified-Since** header set to the Last-Modified date the origin gave it. If the object has not changed, the origin replies **304 Not Modified** with **no body**.

Your browser does the same thing with its own local cache, and today it usually uses `ETag` with `If-None-Match` instead of dates. Open the Network tab, reload a page, and the grey 304s are conditional GETs.

<Deeper kind="beyond" title="CDNs: caches placed by the content provider">

A **content distribution network** (CDN) is the same idea turned around. Instead of the institution installing a cache for its users, the content provider (Netflix, YouTube) or a CDN company (Cloudflare, Akamai) puts caches inside or near many ISPs, and DNS sends each user to a nearby one. When you put Cloudflare in front of your VPS, your VPS becomes the origin server in the figure above and Cloudflare's edge is the proxy cache. The `cf-cache-status: HIT` response header tells you which path a request took. Kurose covers CDNs in 2.6.3.
