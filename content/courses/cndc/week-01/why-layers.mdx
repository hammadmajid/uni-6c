You already layer things: HTTP handlers on a framework on a socket library on the kernel. Networking formalised that instinct in 1984. The exam wants both formalisations drawn from memory, plus the encapsulation that makes them work.

Without layers: **A × L** implementations, and every new link technology forces every application on earth to change.

With layers: **A + L**. Applications talk to one interface (IP and transport), each link technology implements that interface once. The Internet went from dial-up to fiber to 5G without HTTP changing. That is the architecture, not luck.

</Predict>

## What a layer is

Each layer does some work of its own, **uses the service** of the layer below, and **provides a service** to the layer above. The set of services it offers upward is its **service model**; the layer above needs only that, never the implementation. TCP does not know whether the datagram went over Ethernet or Wi-Fi.

<Callout type="exam" title="Advantages and drawbacks, as the marker wants them">
**For**: modularity (discuss and update pieces independently); transparency (a layer's internals can change if its service does not); shared vocabulary ("the transport layer" means one thing everywhere). **Against**: duplicated functionality (error recovery at link and again at transport); layer violations (a strict stack forbids the application from seeing a link-layer timestamp it might want). Two advantages and one drawback earns full marks.
</Callout>

## Encapsulation

The application produces a **message**. Transport prepends a header (ports, sequence numbers): a **segment**. Network prepends IP addresses: a **datagram**. Link prepends MAC addresses and appends a checksum trailer: a **frame**. Physical turns the frame into signals. Each PDU is a header plus the whole PDU from the layer above, nested like JSON inside JSON.

<Callout type="pitfall" title="Four layers or five?">
Some books merge physical and link into one "network access" layer and call TCP/IP four layers. Kurose and Forouzan both use five. Answer with the numbering the question uses, and say so in one line.
</Callout>

<Deeper kind="history" title="Why OSI lost and why we still teach it">

ISO designed OSI top-down by committee. TCP/IP grew bottom-up inside ARPANET and shipped as working code in BSD Unix, so every university had it for free before OSI implementations arrived. The protocols lost; the vocabulary won. Nobody runs the OSI session layer, but everyone says "layer 2 switch", "layer 3 routing" and "layer 7 load balancer" using OSI's numbers.

</Deeper>

<Deeper kind="exam" title="Model answer: compare the OSI and TCP/IP models (5 marks)">

The figure above, as a table:

| Aspect | OSI | TCP/IP |
|---|---|---|
| Layers | Seven: physical, data link, network, transport, session, presentation, application | Five (or four): physical, link, network, transport, application |
| Origin | ISO, reference model designed before implementation | Developed with ARPANET, protocols came first, model described them after |
| Presentation and session | Separate layers | Handled inside the application layer |
| Protocol dependence | Generic model, protocol independent | Model built around specific protocols: IP, TCP, UDP |
| Usage today | Reference and vocabulary (layer numbers) | The actual Internet |

Then one sentence: "OSI is the conceptual reference; TCP/IP is the deployed architecture, and its layers map onto OSI's with presentation and session folded into application."

</Deeper>
