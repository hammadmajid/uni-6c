## Data, database, DBMS

**Data** are known facts that can be recorded and have implicit meaning: a name, a phone number, a book's price. They come in types: integer, float, string, image.

A **database** is a collection of related data. Elmasri adds three implicit properties, and exam answers that list them get full marks:

1. It represents some aspect of the real world, called the **miniworld** or **universe of discourse (UoD)**. Changes to the miniworld are reflected in the database.
2. It is a **logically coherent** collection of data with inherent meaning. A random pile of data is not a database.
3. It is **designed, built and populated for a specific purpose**, with an intended group of users and applications in mind.

The lecture's example is a student database with three tables, all keyed by roll number:

A **DBMS** (database management system) is a general-purpose software system that makes it easier to **define, construct, manipulate and share** databases among various users and applications. It also **protects** the database (from crashes and from unauthorised access) and **maintains** it as requirements change over years. MySQL, PostgreSQL, Oracle and SQL Server are DBMSs; the rows in your Postgres cluster are the database.

The **database system** is the database plus the DBMS software (plus, in some texts, the applications).

## The four things a DBMS does

The slides list the functions of a DBMS. Each one maps to something you type in `psql`:

| Function | What it means | In Postgres |
|---|---|---|
| **Define** | Specify data types, structures and constraints. The definition is stored as metadata in the catalog. | `CREATE TABLE`, `ALTER TABLE` (DDL) |
| **Construct** (load) | Store the data on a storage medium the DBMS controls. | `INSERT`, `COPY` from a CSV |
| **Manipulate** | Query, update, generate reports. | `SELECT`, `UPDATE`, `DELETE` (DML) |
| **Share** | Let many users and programs use it at the same time, correctly. | Hundreds of connections, locks, transactions |

An **application program** reaches the database only by sending **queries** or requests to the DBMS. A query retrieves data; a **transaction** may read some data and write some. Your servlet never opens the table's files; it sends SQL down a JDBC connection and the DBMS does the rest.

## File processing: how it used to be done

Computers were first used for calculation. When businesses adopted them, each department got its own **file processing system**: a set of programs, each with its own data files, producing reports. The slide's university has three:

| Registration file | Library file | Examination file |
|---|---|---|
| RegNo, Name, Father name, Phone, Address, Class | RegNo, Name, Address, Book issued, Fine | RegNo, Name, Father name, Class, Semester, Grade |

Three problems follow from this, and all three are exam points:

1. **Redundancy.** The same fact (name, address) is stored in several files. That wastes storage and, worse, wastes **effort**: every change must be made several times.
2. **Inconsistency.** Because updates are made separately, the copies disagree. The lab above showed it: after one update, which phone number is right?
3. **Program–data dependence.** The structure of each file is written into the programs that read it. Add a field to the registration file and every program that reads it must be changed and recompiled.

The **database approach** keeps a single repository, defined once and accessed by all three applications through the DBMS.

<Deeper kind="exam" title="Model answer: differentiate file processing and the database approach (5 marks)">

**File processing:** each application defines and maintains its own files. Consequences: (1) redundancy, the same data stored in many files, wasting storage and effort; (2) inconsistency, copies updated at different times disagree; (3) program–data dependence, file structure is coded into programs, so changing a file means changing every program; (4) no sharing or concurrent access across departments.

**Database approach:** a single repository, defined once and shared by many users through a DBMS. The definition is stored in a catalog, programs are insulated from storage details, each user can have a view, and the DBMS controls concurrent access and recovery.

Close with the university example: registration, library and exam files each holding the student's name and address, versus one STUDENT table used by all three applications.

</Deeper>

<Deeper kind="history" title="Where the DBMS came from">

The first general-purpose DBMSs appeared in the 1960s: IBM's IMS (hierarchical) for the Apollo programme's parts lists, and CODASYL network databases. Both still tied programs to the physical access paths. In 1970 Edgar Codd at IBM proposed the **relational model**, with data as tables and queries that say what you want, not how to navigate to it. That separation is the data independence you meet in the next lesson. IBM's System R and Berkeley's Ingres built it in the 1970s; Postgres is Ingres's direct descendant ("post-Ingres").

</Deeper>
