## Scenario questions

<Predict
  id="cp1-excel"
  prompt="A university wants to store student records, course enrolments and grades. Why is a DBMS better than keeping them in Excel files? (5 marks)"
  answer="Shared single copy (no redundancy or inconsistency across departments), concurrent multi-user access with transactions, integrity constraints and relationships (an enrolment must reference a real student and course), access control and views per role, backup and recovery, and querying at scale."
>

**Model answer.** Excel files are file processing: each department keeps its own copy, so the same student's phone or address is stored several times and the copies drift apart (**redundancy and inconsistency**). A DBMS stores each fact once in a shared database that every department's application uses.

It also gives what spreadsheets cannot: **concurrent access** by many staff with **transactions** so simultaneous updates do not corrupt data; **integrity constraints** and **relationships** (an enrolment must reference an existing student and course, a grade must be in range); **security and multiple views** (a student sees their grades, finance sees fees); **backup and recovery** after a crash; and **efficient querying** with indexes as records grow to thousands of students over many years.

Five distinct points with one university example each is full marks.

</Predict>

<Predict
  id="cp1-shop"
  prompt="A small shopkeeper sells 15 to 20 items a day and records sales in a notebook. Would a DBMS be suitable? Why or why not? (3 marks)"
  answer="No. Single user, small and simple data that is not expected to change, and the cost and complexity of a DBMS (hardware, licences, training, overhead) outweigh the benefit. A notebook or a spreadsheet is enough."
>

**Model answer.** A DBMS is **not** suitable. The data is small and simple, there is **one user and no concurrent access**, and the structure is not expected to change. The **cost and complexity** of a DBMS (setup, hardware or licences, training, the overhead of security, concurrency control and recovery) would outweigh any benefit. A notebook or a spreadsheet is enough.

Worth one extra sentence: if the shop grows to several branches sharing stock, the answer flips.

</Predict>

<Predict
  id="cp1-hospital"
  prompt="A hospital stores patient records, doctor schedules and billing. Doctors, receptionists and the finance office all need access, but each should see only what they need. Which feature of the database approach solves this, and how? (3 marks)"
  answer="Multiple views with role-based access control: define a view per user group (medical history for doctors, appointments for reception, billing for finance) and grant each role access only to its view."
>

**Model answer.** **Support for multiple views of the data**, combined with **restricting unauthorized access** (role-based access control). The DBA defines a view for each user group over the one shared database: doctors see patients' medical history, receptionists see appointments, finance sees billing only. Each role is granted privileges on its own view and nothing else, so the data is shared but each user sees only what their job needs.

</Predict>

<Predict
  id="cp1-atm"
  prompt="Ali withdraws money at an ATM while his father transfers money into the same account from mobile banking. What can go wrong, and how does the DBMS prevent it? (3 marks)"
  answer="Both read the same balance and each writes its own result, so one update is lost. DBMS transaction management with concurrency control (locking) makes them run as if one after the other, preserving isolation; ACID guarantees the result."
>

**Model answer.** Both transactions read the same balance; each computes a new value and writes it, so the second write **overwrites** the first and one update is **lost** (10,000 − 3,000 and 10,000 + 5,000 can end at 15,000 instead of 12,000). The DBMS's **transaction management and concurrency control** prevent this: the first transaction locks the account row, the second waits, then reads the updated balance. The result is as if they ran one after the other (**isolation**, one of the **ACID** properties).

</Predict>

<Predict
  id="cp1-phone"
  prompt="Sara orders a phone online while another customer orders the last piece of the same model. What could the system do wrong, and what DBMS mechanism stops it? (2 marks)"
  answer="Sell the same phone twice, because both read stock = 1 before either wrote. Concurrency control locks the inventory row until the first transaction completes; the second then sees stock = 0."
>

**Model answer.** Without control, both transactions read stock = 1, both succeed, and the **same phone is sold twice**. **Concurrency control** (locking the inventory row until the transaction commits) makes the second transaction wait; it then reads stock = 0 and reports "sold out".

</Predict>

<Predict
  id="cp1-three-schema"
  prompt="Draw or describe the three-schema architecture and use it to define logical and physical data independence. (5 marks)"
  answer="Three levels: external (user views), conceptual (whole database: entities, relationships, constraints), internal (physical storage and access paths), with mappings between them. Logical independence: change the conceptual schema without changing external schemas or application programs. Physical independence: change the internal schema without changing the conceptual schema."
>

**Model answer.** Draw three stacked boxes: the **external level**, several user views, at the top; the **conceptual level**, the structure of the whole database (entities, data types, relationships, constraints) hiding storage details, in the middle; the **internal level**, the physical storage structures and access paths, at the bottom, above the stored database. Mark the **external/conceptual mapping** and the **conceptual/internal mapping** between them.

**Logical data independence** is the capacity to change the conceptual schema (add a column or a table) without changing external schemas or application programs; only the external/conceptual mapping changes. **Physical data independence** is the capacity to change the internal schema (add an index, reorganise files, move to another disk) without changing the conceptual schema; only the conceptual/internal mapping changes. Physical independence is easier to achieve, because programs never see storage details.

</Predict>
