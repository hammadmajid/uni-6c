## 1. Self-describing: the catalog

A database system holds the data **and a complete description of it**: table names, column types, constraints, which index covers what. That description is **metadata** (data about data), stored in the **DBMS catalog**, also called the data dictionary. The DBMS reads the catalog before every query, which is why the same DBMS software can run a university database and a hospital database.

In file processing, the description lived inside each program. In Postgres it is itself a set of tables you can query:

```sql
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'student';
```

`information_schema` is the SQL-standard view of the catalog; `pg_catalog` is Postgres's own. `\d student` in `psql` is a shortcut that runs catalog queries.

## 2. Insulation between programs and data

The DBMS keeps a description of the data at three levels, the **three-schema architecture** (ANSI/SPARC):

- **External level:** the views each user group sees.
- **Conceptual level:** the whole database for the whole community of users: entities, relationships, constraints. No storage detail.
- **Internal level:** how it is physically stored: files, record layout, indexes.

The DBMS keeps a **mapping** between each pair of neighbouring levels. That mapping is what buys independence.

<ThreeSchemaDiagram />

**Logical data independence**: the capacity to change the **conceptual schema** without having to change **external schemas or application programs**. Adding a column, adding a table, or splitting a table and replacing it with a view of the same shape are all logical changes.

**Physical data independence**: the capacity to change the **internal schema** without having to change the **conceptual schema** (and so without changing external schemas or programs). Adding an index, moving a table to a faster disk, changing the file organisation are all physical changes.

Logical data independence is harder to achieve, because programs depend on the structure they read. Physical independence is nearly total in any relational DBMS.

## 3. Multiple views of the data

A **view** is a subset of the database, or data derived from it, that is not necessarily stored. Each user group gets the view it needs. The slide's example: a student sees their own grades, a teacher sees all grades in a course, finance sees only fee records. In Postgres a view plus a grant does this:

```sql
CREATE VIEW fee_status AS
  SELECT reg_no, name, installment_1, installment_2
  FROM student JOIN fee USING (reg_no);

GRANT SELECT ON fee_status TO finance_office;
```

Finance can now read fees and nothing else. Views are also how logical data independence is kept: if the underlying tables are reorganised, redefine the view and the program reading it never notices.

## 4. Sharing data and multi-user transaction processing

A multi-user DBMS lets many users and programs use the same data at the same moment. That needs **concurrency control**, so that simultaneous updates produce a correct result. The unit of work is the **transaction**: an executing program or process that includes one or more database accesses, such as reading or updating records.

The DBMS guarantees four properties for every transaction, known by their initials:

| Property | Guarantee | What breaks without it | In the lab |
|---|---|---|---|
| **Atomicity** | All of the transaction happens, or none of it. | A transfer debits one account and never credits the other. | Crash mid-transfer, plain writes |
| **Consistency** preservation | A transaction takes the database from one valid state to another; constraints hold before and after. | Stock goes negative; a grade references a student who does not exist. | |
| **Isolation** | A transaction runs as if no other were running at the same time. | Lost updates, double-sold phones. | ATM + deposit, last phone |
| **Durability** | Once committed, changes survive any later failure. | "Payment successful", then a power cut, then no payment. | Crash after COMMIT |

## The lecture's other six

The slide's list continues past these four. In Elmasri they sit under the advantages of using a DBMS, and each is something you have configured in Postgres:

| Slide characteristic | What it means | In Postgres |
|---|---|---|
| **Data integrity and security** | Constraints the DBMS enforces on every write; users authenticated and authorised. | `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK`, `NOT NULL`; roles, `GRANT`, row-level security |
| **Reduced redundancy and inconsistency** | Each fact stored once, so there is nothing to disagree with. | A normalized schema |
| **Backup and recovery** | Restore after a crash or a mistake. | WAL, `pg_dump`, point-in-time recovery, replicas |
| **Relationships** | Link rows across tables and keep the links valid (referential integrity). | Foreign keys, `JOIN` |
| **Scalability and performance** | Stay fast as data grows. | Indexes, partitioning, caching in shared buffers |
| **Transactions (ACID)** | Covered above. | `BEGIN` … `COMMIT` |

<Callout type="exam" title="“No duplicate data” is too strong">
The summary slide says "Less redundancy – no duplicate data". Elmasri's wording is **controlling redundancy**: store each logical item once *by default*, and allow **controlled redundancy** where it helps performance, with the DBMS keeping the copies consistent. Two everyday examples: a foreign key repeats the referenced key by design, and a denormalized reporting table deliberately copies data for speed. Write "reduced, controlled redundancy" and you match both the slide and the book.
</Callout>

## When not to use a DBMS

A DBMS costs something: the licences and hardware, the training, and the overhead of doing security, concurrency control, recovery and integrity checking on every operation. Elmasri says a plain file-based solution may be better when:

1. The database and applications are **simple, well defined, and not expected to change**.
2. There are **stringent real-time requirements** that the DBMS overhead would not meet.
3. It is an **embedded system with limited storage** where a general-purpose DBMS will not fit.
4. There is **no multi-user access** to the data.

1. **Self-describing nature.** The database contains the data and its complete definition (metadata) in the DBMS catalog, so the same DBMS can manage any database and programs need not embed the structure.
2. **Insulation between programs and data, and data abstraction.** Through the three-schema architecture the DBMS provides program–data independence: *logical* (change the conceptual schema without changing external schemas or programs) and *physical* (change the internal schema without changing the conceptual schema). 3. **Support for multiple views.** Each user group can have its own view, a subset or derived form of the data, which also restricts what they can see.

<Deeper kind="why" title="Why isolation is enforced with locks, and what Postgres actually does">

The lab used `SELECT … FOR UPDATE`, which takes a row lock: exactly the "locking inventory until the transaction completes" the slide describes. Postgres's default isolation level (READ COMMITTED) does **not** prevent the lost update if you read with a plain `SELECT` and write back a computed value. Two correct fixes: lock the row with `FOR UPDATE`, or make the update relative (`UPDATE account SET balance = balance - 3000`), which re-reads the current row under a lock. At the SERIALIZABLE level Postgres detects the conflict and aborts one transaction, which the application must retry. You will meet all of this formally when the course reaches transactions.

</Deeper>
