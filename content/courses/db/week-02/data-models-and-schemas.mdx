## 1. What a data model is

The slide's definition, which is Elmasri's: a **data model** is *a collection of concepts that can be used to describe the structure of a database*. "Structure" means three things:

- **data types**: what kind of values are stored,
- **relationships**: how the pieces connect,
- **constraints**: rules the data must obey (every student has a StdNo, no two share one).

A data model is the tool for **data abstraction**: it hides the details of how data is stored and keeps only what matters for understanding it. Most data models also include **basic operations** for retrieval and update, and many let you define **user-defined operations** on top. The slide's examples are *Calculate GPA* and *Update Inventory*.

In systems terms: a data model is the vocabulary a schema is written in. The relational model's vocabulary is tables, columns, keys. The ER model's is entities, attributes, relationships. Your STUDENT table is not a data model; it is a schema written using one.

## 2. Three categories, by how close to the user

<DbDataModelLadder />

| Category | Also called | Concepts it uses | Lecture's examples |
|---|---|---|---|
| **High-level** | conceptual | entities, attributes, relationships | ER model, object-oriented |
| **Representational** | implementation, logical | records: rows and columns, or linked records | relational, network, hierarchical |
| **Low-level** | physical | record formats, record orderings, access paths | files, indexes, B-trees |

**Conceptual models** use concepts close to how users see data. An **entity** is a real-world object or concept (an employee, a project). An **attribute** is a property of interest that describes an entity (the employee's name). A **relationship** is an interaction among entities (an employee works on a project). You meet all three properly in week 3.

**Representational models** are "in between": an end user can understand them, and they are close enough to storage to be implemented directly. They represent data using **record structures**, which is why they are also called record-based models. The relational model is the one used most today; network and hierarchical models are the older ones.

**Physical models** describe how data is stored as files: record formats, the order records are kept in, and **access paths** (an index is an access path: a structure that makes finding a record fast).

### The lecture's four "types of data models"

Slides 12 to 14 then list four types: **relational**, **entity-relationship**, **object-oriented** and **semi-structured**. These are specific models, and they sit on different rungs of the ladder:

| Model | What it is | Rung |
|---|---|---|
| Relational | Data in tables (relations) of rows and columns | representational |
| Entity-relationship | Entities, their attributes, and relationships among them; a set of same-type entities is an **entity set**, of same-type relationships a **relationship set** | conceptual |
| Object-oriented | ER plus functions (methods), encapsulation and object identity; rich types including structured and collection types | conceptual, close to implementation |
| Semi-structured | Data with tags or markers that separate fields and nest them, without a fixed table shape: XML, JSON | representational, self-describing |

The semi-structured model is the one you use daily. A JSON document carries its field names with each record, so two records can have different fields:

```json
[
  { "name": "Saman", "stdNo": "040342", "phones": ["0300-1234567", "051-7654321"] },
  { "name": "Dinesh", "stdNo": "030231", "field": "ENT" }
]
```

Postgres stores this directly in a `jsonb` column, next to ordinary relational columns.

<Callout type="exam" title="Three places the slides mix up the categories">
- **Slide 13** calls the ER model "the **logical** representation of data as objects and relationships". Reproduce that line if asked for the lecture's definition, but the ER model is a **conceptual** (high-level) model. "Logical" is the usual name for the representational level, where the relational model sits.
- **Slide 12** calls relational, ER, object-oriented and semi-structured "four data models used for understanding the structure of the database", as if they were one list of alternatives. They are models from different categories. If a question asks for the **categories**, answer high-level, representational, low-level; if it asks for **types** "according to the lecture", give the four.
- **Lecture 3's recap slide** lists "External Views (customer, manager, auditor)" as a fourth category of data model. External views belong to the **three-schema architecture**; they are not a kind of data model.
</Callout>

## 3. Schema versus database state

It is important to distinguish between the **description** of a database and the **database itself**.

- The **database schema** is the description. It is specified during design and is **not expected to change frequently**. Elmasri also calls it the **intension**.
- A **schema diagram** is the conventional way a data model displays a schema: each table's name and its columns, no data.
- Each object in the schema, such as STUDENT or COURSE, is a **schema construct**.
- The **database state** is the data in the database at a particular moment. It is also called the **extension**, a **snapshot**, or the current set of **instances** (occurrences).

Step through what happens to the lecture's STUDENT table.

<DbSchemaVsState />

The vocabulary the stepper walked through, in the order it happens:

| Term | Meaning |
|---|---|
| **Empty state** | Schema defined to the DBMS, no data yet |
| **Initial state** | The database first populated or loaded with data |
| **Current state** | The state at this moment; every insert, delete or update produces a new one |
| **Valid state** | A state that satisfies the structure and constraints in the schema. The DBMS guarantees every state is valid, by rejecting writes that would break a constraint |
| **Schema evolution** | A change to the schema itself, made only when requirements change (a new data item to store for each record) |

<Callout type="key-idea" title="A memory hook from your own work">
A migration file is schema evolution. The rows your app writes all day are state changes. Your team reviews migrations carefully because they are rare and change the intension; nobody reviews an INSERT.
</Callout>

## 4. The three levels again, through the lecture's example

Week 1's lesson on the database approach taught the three-schema architecture and both kinds of data independence. Slide 18 shows the same idea with one employee:

| Level | What it holds for Fatima Abdullah |
|---|---|
| **External** (two views) | *Employee Data*: first name Fatima, last name Abdullah, DOB 12 Sept 1980. *Workers*: name F. Abdullah, age 34 Y 10 d, department Sales |
| **Conceptual** | One table row: Name, DOB, Dependent (5), Dep. Id (D019) |
| **Internal** | A stored record with a header: RH, Fatima Abdullah 12081980 5 D019 |
| Below the DBMS | The operating system's bits on disk |

Two things to see. First, the two external views show the **same stored fact differently**: one splits the name, the other abbreviates it, and "Age 34 Y, 10 d" is not stored anywhere; it is computed from DOB when the view is read. Second, the arrows between levels are **mappings**: external/conceptual and conceptual/internal. Changing one level means updating a mapping, not the levels on either side of it. That is data independence.

The slide also labels which kind of data model describes each level: a **conceptual** model at the external level, a **representational** model at the conceptual level, a **physical** model at the internal level. Elmasri's version is that external and conceptual schemas are usually implemented in a representational model, often designed first in a high-level one.

<Deeper kind="exam" title="Model answer: differentiate between a data model, a schema and an instance, with examples (5 marks)">

- A **data model** is a collection of concepts used to describe the structure of a database: its data types, relationships and constraints, usually with basic retrieval and update operations. It is the vocabulary, not a particular database. *Example: the relational model (tables, columns, keys); the ER model (entities, attributes, relationships).*
- A **schema** (intension) is the description of one particular database, written in a data model's concepts. It is specified at design time, shown as a schema diagram, and rarely changes; a change is called schema evolution. *Example: STUDENT(Name, StdNo, Level, Field), COURSE(Name, Code, Credits, Department).*
- An **instance** or **database state** (extension, snapshot) is the data in the database at a particular moment. Every insert, delete or update produces a new state, and the DBMS ensures each one is valid against the schema. *Example: the two rows (Saman, 040342, 3, CSE) and (Dinesh, 030231, 4, ENT).*

One line to finish: the schema is fixed while the state changes constantly, and one data model can describe many different schemas.

</Deeper>

<Deeper kind="exam" title="Model answer: explain the categories of data models (5 marks)">

Data models are categorised by the concepts they use to describe the database structure.

1. **High-level or conceptual** models use concepts close to how users perceive data: entities (real-world objects such as EMPLOYEE), attributes (properties such as the employee's name) and relationships (such as WORKS_ON). Example: the ER model.
2. **Representational or implementation** models are understood by end users but are close to how data is organised in the computer. They hide some storage details but can be implemented directly, and represent data with record structures. Examples: relational (most used), network and hierarchical.
3. **Low-level or physical** models describe how data is stored in files: record formats, record orderings and access paths such as indexes.

A labelled ladder (users at the top, disk at the bottom) earns the diagram mark.

</Deeper>
