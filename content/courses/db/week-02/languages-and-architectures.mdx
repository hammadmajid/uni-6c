**Two reasons, and the lecture names both.** First, **security**: to let browsers connect, Postgres would have to be exposed to the internet, and every client would need database credentials. Anyone could open the dev tools, copy them, and run any SQL they like. ## 1. Database languages

Lecture 2 names three:

- **Data Definition Language (DDL)**: used to **define schemas**. `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `CREATE VIEW`.
- **Data Manipulation Language (DML)**: used to **retrieve, insert, delete and modify** data. `SELECT`, `INSERT`, `DELETE`, `UPDATE`.
- **Structured Query Language (SQL)**: a comprehensive language that **combines both** DDL and DML (and more: constraints, views, transactions, security).

The test for any statement: does it change the **schema** or the **state**? Last lesson's vocabulary is the whole trick.

<Deeper kind="beyond" title="Elmasri's fuller list: SDL, VDL, and procedural versus declarative DML">

The textbook splits definition further. The **storage definition language (SDL)** specifies the internal schema; the **view definition language (VDL)** specifies external schemas. In real DBMSs there is no separate SDL (storage is set by parameters and statements like `CREATE INDEX` or tablespaces), and SQL's DDL covers views, so the lecture's two-way split is what you need.

DML also comes in two kinds. A **high-level or nonprocedural (declarative)** DML such as SQL says *what* to retrieve, in one statement that may return many records (set-at-a-time). A **low-level or procedural** DML retrieves one record at a time and needs loops in a host language (record-at-a-time), which is what network and hierarchical systems used. When DML statements are embedded in a general-purpose language like Java, that language is the **host language** and the DML is the **data sublanguage**. JDBC is the modern version: SQL strings inside Java.

</Deeper>

## 2. What is inside a DBMS

A DBMS is a complex software system. Slide 21 (Elmasri's Figure 2.3) splits it into two halves: the **top half** is the users of the database system and the tools they work through, the **bottom half** is the internals that store the data and process transactions. Follow each kind of user through it.

<DbModulesDiagram />

| Module | Job |
|---|---|
| **DDL compiler** | Processes schema definitions and stores them in the catalog |
| **System catalog / data dictionary** | The metadata: names, types, constraints, storage details, statistics. Read by nearly every other module |
| **Query compiler** | Parses and validates an interactive query |
| **Query optimizer** | Rearranges the query and picks the cheapest execution plan, using catalog statistics |
| **Precompiler** | Pulls DML commands out of an application program written in a host language |
| **DML compiler** | Compiles those DML commands into object code for database access |
| **Host language compiler** | Compiles the rest of the program; linked with the DML part into a **canned (compiled) transaction** |
| **Runtime database processor** | Executes everything: privileged commands, query plans, canned transactions |
| **Stored data manager** | Controls access to data on disk; works with the OS and the buffers |
| **Concurrency control, backup, recovery** | Integrated with the runtime processor to give transactions their ACID properties |

These are the actors from week 1 again. The DBA uses DDL and privileged commands. **Casual users** type interactive queries. **Application programmers** write the programs. **Parametric (naive) users** only run the canned transactions the programmers built: the bank teller pressing "withdraw".

<Deeper kind="beyond" title="The summary slide also lists DBMS interfaces and classification criteria">

Lecture 2's summary names two topics that have no slides of their own. In case either appears, here is Elmasri's list in one line each.

**Interfaces:** menu-based (web browsing), apps for mobile devices, forms-based (fill in a form to insert or query), graphical (point and click on a schema diagram), natural-language and keyword search, speech, **interfaces for parametric users** (a small set of commands or keys for canned transactions), and **interfaces for the DBA** (privileged commands).

**Classification criteria:** by **data model** (relational, object, document, graph, key-value…), by **number of users** (single-user or multi-user), by **number of sites** (centralized or distributed; homogeneous or heterogeneous), by **cost**, and by **purpose** (general-purpose or special-purpose, such as an airline reservation system).

## 3. Where the DBMS runs: centralized, two-tier, three-tier

Toggle between the three architectures and watch where each layer runs.

<DbTiersDiagram />

**Centralized.** All DBMS functionality, application programs and user-interface processing run on **one machine**. Users sat at terminals that only displayed output. This is the mainframe era.

**Two-tier client/server.** Built for networks of PCs and workstations. A **client** is a user machine with user-interface capabilities and local processing. A **server** is a system of hardware and software that provides services to clients. In the two-tier DBMS version, the client runs the interface **and the application programs**, and connects straight to the DBMS on the server through an API such as **ODBC** or **JDBC**. The server is called a query server or transaction server. It is "two-tier" because the software is split over two systems.

**Three-tier.** The Web changed the roles and added a **middle tier**, called the **application server** or **web server**:

- **Presentation layer** (client): displays information and takes input. Usually a browser.
- **Business logic layer** (middle tier): applies rules and constraints before data goes up to the user or down to the DBMS. Your servlet on Tomcat.
- **Database services layer** (DB server): the DBMS.

The slide's security point: the **database server is only accessible through the middle tier**. Clients cannot reach it directly, so they never hold database credentials and the rules cannot be bypassed.

<Callout type="exam" title="The slide's version of n-tier">
Slide 28 says: "If the **bottom layer** is split into two layers (a web server and a database server), then it is a 4-tier architecture." Reproduce it if asked for the lecture's wording. It is backwards against the textbook: the web server is not part of the bottom layer. Elmasri says n-tier (four or five tiers) arises by dividing the layers between the user and the stored data further, **typically the business logic layer**: for example a web server in front of a separate application server, in front of the database server.
</Callout>

<Deeper kind="exam" title="Model answer: compare two-tier and three-tier client/server architecture (6 marks)">

**Two-tier.** Software is split over two systems. The **client** runs the user interface and the application programs; the **server** runs the DBMS (a query or transaction server). The client connects directly to the DBMS through ODBC or JDBC. *Example: a desktop billing app on each counter PC connecting to a MySQL server on the LAN.*

**Three-tier.** An intermediate **application server or web server** is added between them. The client handles **presentation**, the middle tier handles **business logic** (rules and constraints on data going up or down), and the database server provides **database services**. *Example: a browser, a Java servlet on Tomcat, and PostgreSQL.*

| | Two-tier | Three-tier |
|---|---|---|
| Where application logic runs | Client | Middle tier |
| Client talks to | DBMS directly | Middle tier only |
| Security | Every client holds DB credentials | DB server reachable only from the middle tier |
| Updating the app | Reinstall on every client | Update the server once |
| Scale | Many DB connections, one per client | Middle tier pools connections |
