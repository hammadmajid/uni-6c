Lecture 3 opens the design half of the course. Before you can write a single `CREATE TABLE`, you draw what the organisation cares about as an **ER diagram**. This lesson covers the "things" and their properties. Relationships and keys come in the next one.

<Predict
  id="one-row"
  prompt="SZABIST wants to store, for every student: registration number, full name (first and last), all their phone numbers, date of birth, and age. You have to fit each student into ONE row of ONE table. Which of those five things cause trouble, and what trouble?"
  answer="Phone numbers: a student can have several, and one cell cannot hold a set cleanly. Age: it can be computed from date of birth, so a stored copy goes stale every birthday. Full name: it has parts, so you must decide whether to keep one column or two. Registration number and date of birth fit fine."
>

Three of the five have a problem, and each one is a different **attribute type**:

- **Phone numbers** are **multivalued**: one student, a set of values. A single cell cannot hold a set cleanly.
- **Age** is **derived**: it can always be computed from date of birth. A stored copy is wrong after the next birthday.
- **Full name** is **composite**: one value made of parts (first, last). You have to decide whether the parts matter on their own.

The ER model marks each of these with its own symbol, so the problem shows on the diagram long before it causes a bug in a table. When you map the diagram to tables later, each symbol tells you what to do: a multivalued attribute becomes its own table, and a derived one is usually not stored.

</Predict>

## 1. Where the ER diagram fits

Database design runs in stages. The lecture lists them on slide 7. Put them in order before reading on.

  topLabel="First"
  bottomLabel="Last"

The four stages that matter for the exam, with the running university example from the slides:

| Stage | Output | University example |
|---|---|---|
| Requirements collection and analysis | Data requirements and functional requirements | "Track students, courses, instructors" |
| **Conceptual design** | Conceptual schema, drawn as an **ER diagram** | STUDENT, ENROLLS, COURSE |
| Logical design (data model mapping) | Database schema in the DBMS's data model: tables and keys | `student`, `course`, `enrollment` tables |
| Physical design | Storage structures, indexes, access paths | An index on `enrollment(course_id)` |

A **conceptual data model** describes *what* data is needed, not *how* it is stored. The slide's analogy: it is the blueprint of a house, not the bricks. That is why it is **DBMS-independent**. The same ER diagram can become a Postgres, MySQL or Oracle schema. It is also readable by non-technical users, so the registrar can check it before anything is built.

The ER model was introduced by **Peter Chen in 1976**. The notation you will draw is his, as extended in Elmasri: rectangles, ovals and diamonds.

<Callout type="key-idea" title="ERD versus UML class diagram">
The slides pair them. Use an **ERD** to design a database schema: entities, attributes, relationships. Use a **UML class diagram** to design software: classes with methods, inheritance, interactions. A class diagram can model the same data, and developers often convert one into the other. As a backend developer you already read class diagrams. The ERD is the same idea without methods, and with its own symbols.
</Callout>

## 2. Entities: type, instance, set

An **entity** is a real-world object or concept with an independent existence that the organisation wants to store data about: a student, a course, an employee, a car. It can be physical (a car) or conceptual (a course, a job).

Three words that the exam separates:

| Term | Definition | University | Car rental |
|---|---|---|---|
| **Entity type** | The category: a set of entities that share the same attributes | STUDENT | CAR |
| **Entity instance** | One specific entity of that type | Ali Khan, 2312200 | Toyota Corolla 2020, LEA-1234 |
| **Entity set** | All instances of the type in the database at one moment | Every SZABIST student today | Every car in the fleet today |

The entity type is the design; it stays the same. The entity set changes every time a student joins or leaves. That is the same split as schema versus state from lecture 2.

<Callout type="exam" title="“Entity set is equivalent to a table”: which part of the table?">
Slide 34 says an entity set is "equivalent to a table in a relational database". Slide 33 says entity types are "used to define database tables". Both are half right, and they are not the same half:

- The **entity type** becomes the table's **definition**: its name and columns (`CREATE TABLE student`).
- The **entity set** becomes the table's **rows** at a given moment.

If the question says "according to the lecture", write the slide's line. Otherwise write "an entity type maps to a table, and the entity set is the set of rows in it at a given time". That answer is correct for either marker.
</Callout>

### Strong and weak entities

A **strong** (regular) entity type has a key of its own: STUDENT has RegNo. A **weak** entity type does not. It is identified only through its relationship to an **owner** entity. The slide's pairs:

- **EMPLOYEE → DEPENDENT.** A dependent is identified by the employee plus the dependent's name. Two employees can both have a daughter named Fatima.
- **BOOK → BOOKCOPY.** Copy number 3 means nothing until you say which book.
- **ORDER → ORDER ITEM.** Line 2 means nothing without the order.

A weak entity is drawn as a **double rectangle**. It is linked to its owner by an **identifying relationship** (a double diamond). The attribute that tells one weak entity apart from the others with the same owner is its **partial key**, underlined with a dashed line.

<Callout type="exam" title="The slide's definition of a weak entity, and the precise one">
The slide says a strong entity "can exist independently" and a weak one "depends on a strong entity". Write that if asked for the lecture's words. Elmasri's definition is sharper: a weak entity type **does not have key attributes of its own**. It is identified by its owner's key plus its partial key. Existence dependence follows from that, but it is not the definition. An ORDER ITEM depends on an ORDER *because* "item 2" identifies nothing on its own.

One more trap: the lecture PDF shows the weak entity box and the multivalued oval with one thick border. The original slides use **double** lines, and the thick line is an artefact of the file conversion. Draw two clearly separate lines on paper.
</Callout>

### Naming entity types

The slide's conventions, which examiners do check on a hand-drawn ERD:

- **Singular** names: STUDENT, not STUDENTS. The box names the type, and each instance is one student.
- **Capital letters** for entity types, so they stand apart from attribute names.
- Use the **organisation's own word**: CUSTOMER or CLIENT, whichever they use.
- Abbreviate consistently if at all (EMP, CUST, PROD). Use no spaces or special characters, and avoid SQL keywords such as TABLE, INDEX, SELECT and ORDER.

Watch that last rule: ORDER is a reserved word in SQL, so real schemas often call the entity ORDERS or SALES_ORDER. It is fine to draw ORDER in the ERD.

## 4. Attributes: four pairs and two extras

An **attribute** is a property that describes an entity: a student's name, CNIC, date of birth. Each is an oval joined to its entity by a line. The lecture classifies attributes along independent axes, so one attribute has several labels at once. Age, for example, is simple, single-valued *and* derived.

| Axis | One side | Other side | Symbol for the marked side |
|---|---|---|---|
| Has parts? | **Simple (atomic)**: Age, Salary, Gender | **Composite**: Name (First, Last), Address (Street, City, Zip) | Sub-ovals hanging off the oval |
| How many values? | **Single-valued**: RegNo, DOB | **Multivalued**: Phone numbers, Emails | Double oval |
| Stored or computed? | **Stored**: DOB | **Derived**: Age from DOB, Total salary from base plus bonus | Dashed oval |
| Identifies the entity? | Ordinary attribute | **Key attribute**: RegNo | Name underlined |

Two more from the slides:

- **NULL values.** Some attributes have no value for some entities. A person with no middle name has NULL for MiddleName. An optional emergency contact is NULL if it was not given. NULL means *not applicable* or *unknown*. It does not mean zero or an empty string.
- **Complex attributes.** Composite and multivalued nested together. The slide's example is Educational Qualifications: many degrees (multivalued), each with DegreeName, University and Year (composite).

### The COMPANY preliminary design

Slide 52 is Elmasri's Figure 3.8: the COMPANY database's four entity types before relationships exist. Every connection between entities is written as an attribute for now:

| Entity type | Attributes as drawn on the slide |
|---|---|
| EMPLOYEE | Name (composite: Fname, Minit, Lname), Ssn (key), Sex, Address, Salary, Birth_date, **Department**, **Supervisor**, **Works_on** (multivalued, composite: Project, Hours) |
| DEPARTMENT | Name (key), Number (key), **Locations** (multivalued), **Manager**, Manager_start_date |
| PROJECT | Name (key), Number (key), Location, **Controlling_department** |
| DEPENDENT | **Employee**, Dependent_name, Sex, Birth_date, Relationship |

Two details to notice. DEPARTMENT and PROJECT each have **two** key attributes, both underlined, because both Name and Number are unique. DEPENDENT has no key at all. It is a weak entity waiting to be recognised.

<Predict
  id="company-refine"
  prompt="The figure's caption says some of these attributes “will be refined into relationships”. Which ones? Name at least four, and say what each one really connects."
  answer="EMPLOYEE.Department (employee works for department), EMPLOYEE.Supervisor (employee supervises employee), EMPLOYEE.Works_on (employee works on project, with Hours), DEPARTMENT.Manager (employee manages department), PROJECT.Controlling_department (department controls project), DEPENDENT.Employee (employee has dependents, which makes DEPENDENT weak)."

**Rule of thumb:** an attribute whose value *is another entity* is a relationship in disguise.

| Attribute | Becomes relationship | Connects |
|---|---|---|
| EMPLOYEE.Department | WORKS_FOR | EMPLOYEE, DEPARTMENT |
| DEPARTMENT.Manager (+ Manager_start_date) | MANAGES, with attribute StartDate | EMPLOYEE, DEPARTMENT |
| PROJECT.Controlling_department | CONTROLS | DEPARTMENT, PROJECT |
| EMPLOYEE.Supervisor | SUPERVISION | EMPLOYEE, EMPLOYEE (a recursive relationship) |
| EMPLOYEE.Works_on (Project, Hours) | WORKS_ON, with attribute Hours | EMPLOYEE, PROJECT |
| DEPENDENT.Employee | DEPENDENTS_OF (identifying) | EMPLOYEE, DEPENDENT (weak) |

Hours moves onto the relationship because it describes the *pair* (this employee on this project), not either entity alone. The next lesson draws these as diamonds.

<Deeper kind="exam" title="Model answer: explain the types of attributes with examples and ER notation (5 marks)">

An attribute is a property that describes an entity type, drawn as an oval joined to its entity.

1. **Simple (atomic) vs composite.** A simple attribute cannot be divided (Age, Gender). A composite attribute has component attributes (Name → FirstName, LastName; Address → Street, City). Draw sub-ovals joined to the composite oval.
2. **Single-valued vs multivalued.** Single-valued: one value per entity (DateOfBirth). Multivalued: a set of values (PhoneNumbers). Draw a **double oval**.
3. **Stored vs derived.** Derived values are computed from other attributes (Age from DateOfBirth). Draw a **dashed oval**.
4. **Key attribute.** Its value is unique for each entity (StudentID). **Underline** the name.
5. **NULL.** The value is missing or not applicable (MiddleName).
6. **Complex.** Composite and multivalued nested (Qualifications: several degrees, each with DegreeName, University, Year).

Sketch one small entity showing all the symbols, for example the EMPLOYEE example above. A diagram earns marks that prose alone does not.

</Deeper>

<Deeper kind="formal" title="Elmasri's text notation for complex attributes">

Elmasri writes attribute structure in text as well. Parentheses group the parts of a composite attribute, braces mark a multivalued one, and commas separate components. The textbook's example is a person with several residences, each with several phones:

```text
{AddressPhone( {Phone(AreaCode, PhoneNumber)},
               Address(StreetAddress(Number, Street, ApartmentNumber),
                       City, State, Zip) )}
```

Read it from outside in: many AddressPhone values. Each one has a set of phones (each phone composite) and one composite address, whose StreetAddress is itself composite. The lecture does not use this notation, so it is unlikely on the quiz. It is the precise answer to "what is a complex attribute".

</Deeper>

<Deeper kind="why" title="Why the model distinguishes multivalued and derived at all">

Both are warnings about the table you will get. A **multivalued** attribute cannot sit in one column of a relational table without breaking first normal form, which you meet later in the course. Mapping moves it into a separate table keyed by the owner plus the value, for example `student_phone(reg_no, phone)`. A **derived** attribute is usually not stored at all. It is computed in a query or a view, so it cannot drift out of sync. In Postgres, `GENERATED ALWAYS AS (…) STORED` is the one case where the DBMS stores it and keeps it correct for you. That only works for expressions of the same row, not "years since hiring", which depends on today's date.

</Deeper>
