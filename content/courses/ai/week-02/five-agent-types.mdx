## 1. Simple reflex agent

It chooses actions **only on the current percept**, using **condition–action rules**: if condition then action. The lecture's example is a frog:

| Percept (size, motion) | Action |
|---|---|
| Small moving object | SNAP |
| Large moving object | AVOID (and inhibit SNAP) |
| Not moving | NOOP (the default, needed for completeness) |

The vacuum agent from the last lesson is one. So is a thermostat, and so is a firewall rule list. In backend terms this is a **stateless request handler**: the same request always gets the same response.

The catch, stated on the slide: it is rational only if the right decision can be made from the current percept alone, which means the environment must be **fully observable**. In a partially observable world it gets stuck in loops. A vacuum with no location sensor cannot tell A from B, and with only "Right" and "Left" rules it may push against a wall forever. (Randomising the action sometimes gets it out.)

## 2. Model-based reflex agent

It keeps an **internal state**: a representation of the parts of the world it cannot currently see, built from the percept history. Updating that state needs a **model**, knowledge of "how things happen in the world", in two parts:

- **How the world evolves** on its own (other cars keep moving while you look away).
- **What my actions do** (turning the wheel left moves me left).

Then it still picks an action with **rules**, but the rules look at the state, not just the percept. The lecture's table agent:

| If (state built from percepts) | Then |
|---|---|
| Saw an object ahead, turned right, and now it is clear ahead | Go straight |
| Saw an object ahead, turned right, and there is an object ahead again | Halt |
| See no objects ahead | Go straight |
| See an object ahead | Turn randomly |

The first two rows are the whole point. The percept "clear ahead" means different things depending on **what happened before**, and only an agent with memory can tell.

For an engineer, the internal state is a **cache of world state** and the model is what tells you when the cache has gone stale. That is exactly the re-check slider in the vacuum lab: a model-based agent with a wrong model of how the world evolves ("clean stays clean") did worse than one with no memory at all.

<Deeper kind="edge" title="The wall-following robot (the lecture's longer example)">

Actions: left, right, straight, open-door. The rules read the current walls, but the robot also needs to remember which way it has been going to follow a wall around a maze without retracing:

1. open left, open right, open straight → choose randomly between left and right
2. wall left, open right, open straight → straight
3. wall right, open left, open straight → straight
4. wall right, open left, wall straight → left
5. wall left, open right, wall straight → right
6. wall left, door right, wall straight → open-door
7. wall right, wall left, open straight → straight
8. default → move randomly

Rules 1 to 7 on their own are a simple reflex agent. The slide calls it "a reflex agent with internal state" because following a wall around corners needs the robot to remember which side the wall was on.

</Deeper>

## 3. Goal-based agent

It chooses actions **to achieve goals**, where a goal is a description of desirable situations. To do that it must look ahead: "what will the world be like **if I do action A**?". The slide's chain:

> brake light → the car in front is stopping → I should stop → I should use the brake

When the goal is far away (a route across a city, a sequence of moves in a puzzle), looking ahead one step is not enough, and the agent needs **search** and **planning**. That is the next several weeks of this course and of the AI lab.

Why it is **more flexible than a reflex agent**: the knowledge behind each decision is explicit, so you can change it. A reflex taxi needs a new rule table for every destination; a goal-based taxi takes the destination as input.

## 4. Utility-based agent

Goals are binary: reached or not. A **utility function** gives each state a number, how "happy" the agent would be there, so it can compare outcomes that all reach the goal. The slide lists when goals are not enough:

- **Conflicting goals**, only some of which can be achieved: fast versus safe, cheap versus comfortable. Utility says how to trade them.
- **Uncertainty**: several goals, none certain. You weigh the **likelihood** of success against the **importance** of each goal.

A rational utility-based agent picks the action with the highest **expected** utility. This is the same "expected" as in the definition of rationality, and it is how every scheduler with a cost function works: a Kubernetes scheduler scoring nodes, a query planner costing plans, a ride-hailing dispatcher trading pickup time against driver idle time.

## 5. Learning agent

Any of the four agents above can be wrapped so it **improves with experience**. The slide's four components:

| Component | Job | Systems analogy |
|---|---|---|
| **Performance element** | Selects external actions. This is "what was previously the whole agent". | The production service |
| **Critic** | Tells the learning element how well the agent is doing against a **fixed performance standard** | Monitoring against an SLO |
| **Learning element** | Makes improvements to the performance element | The team shipping fixes |
| **Problem generator** | Suggests actions that lead to new, informative experiences | Canary releases and A/B experiments |

The critic needs an **external** standard. The agent's own percepts cannot tell it whether it did well. A chess program sees that it is checkmated, but only the standard says checkmate is bad.

The problem generator is what makes the agent **explore**. Without it the agent only ever repeats what currently looks best and never finds anything better, the classic exploration-versus-exploitation trade-off.

## All five in one table

| Type | Decides using | Handles | Breaks when |
|---|---|---|---|
| Simple reflex | Current percept + condition–action rules | Fully observable, simple worlds | Anything relevant is not visible right now |
| Model-based reflex | Internal state + model + rules | Partial observability | Its model of the world is wrong |
| Goal-based | Model + goals + look-ahead (search, planning) | New situations; goals that change | Several ways reach the goal and some are better |
| Utility-based | Model + utility function, maximising expected utility | Conflicting goals, uncertainty | The utility function is badly designed |
| Learning | A critic, a learning element and a problem generator around any of the above | Unknown or changing environments | The performance standard is wrong |

1. **Simple reflex**: acts on the current percept only, using condition–action rules. Rational only in a fully observable environment.
