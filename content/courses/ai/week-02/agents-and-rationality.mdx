## Agents: the vocabulary

> An **agent** is anything that can be viewed as perceiving its environment through **sensors** and acting upon that environment through **actuators**.

<AiAgentLoop />

| Agent | Sensors | Actuators |
|---|---|---|
| Human | Eyes, ears, other organs | Hands, legs, mouth, other body parts |
| Robot | Cameras, infrared range finders | Various motors |
| Software | Keystrokes, file contents, network packets (encoded bit strings) | Displaying output, writing files, sending packets |

The terms quizzes ask you to define, word for word:

| Term | Meaning |
|---|---|
| **Percept** | The agent's perceptual input at one instant. |
| **Percept sequence** | The complete history of everything the agent has perceived so far. |
| **Agent function** | A mathematical map from percept sequences to actions: F : P* → A. |
| **Agent program** | The code that implements the agent function on a physical system. |
| **Architecture** | The device with sensors and actuators that the program runs on. |
| **Performance measure** | The criterion that decides how successful the agent is. |
| **Behaviour** | The action the agent performs after a given sequence of percepts. |

The slide writes the function twice. First a = F(p): the action depends only on the **current percept**. Then aₖ = F(p₀ p₁ … pₖ): in general the action can depend on **everything perceived so far**, so F maps **percept sequences** to actions. The star in P* means "sequences of any length".

**Agent = architecture + program.** A backend analogy: the agent function is the **spec**, a possibly infinite table saying what to return for every possible request history. The agent program is the **service** that implements it in finite code. The architecture is the machine it is deployed on.

## The vacuum-cleaner world

The lecture's running example (R&N figure 2.2). Two squares, A and B. **Percept**: which square am I in, and is it dirty? **Actions**: Left, Right, Suck, NoOp. The start of its agent function as a table:

| Percept sequence | Action |
|---|---|
| [A, Clean] | Right |
| [A, Dirty] | Suck |
| [B, Clean] | Left |
| [B, Dirty] | Suck |
| [A, Clean], [A, Clean] | Right |
| [A, Clean], [A, Dirty] | Suck |
| … | … |

And a program that implements it in four lines, instead of an infinite table:

```text
function REFLEX-VACUUM-AGENT([location, status]) returns an action
    if status = Dirty then return Suck
    else if location = A then return Right
    else if location = B then return Left
```

The table grows without end, one row per possible history. The program ignores history entirely and still produces the same actions. That gap is why AI is about writing **programs**, not tables.

## Rationality

The lecture's list: a **rational agent** does the expected action that maximises its **performance measure**, based on its **percept sequence** and its **built-in knowledge**. What is rational at any moment depends on four things:

1. The **performance measure** that defines success.
2. The agent's **percept sequence** to date.
3. The agent's **prior knowledge** of the environment.
4. The **actions** the agent can perform.

The textbook's definition, the one to quote:

> For each possible percept sequence, a rational agent should select an action that is **expected** to maximise its performance measure, given the evidence provided by the percept sequence and whatever built-in knowledge the agent has.

The key word is **expected**. Rational is not the same as **omniscient** (knowing the actual outcome) or **perfect**. Russell and Norvig's example: you look both ways, the road is clear, you cross, and a cargo door falls off a passing airliner and flattens you. Crossing was still rational. You chose the best action given what you could perceive.

The systems version: a load balancer sends a request to the backend whose last health check was green. The backend dies a millisecond later and the request fails. The routing decision was still correct. It was the best choice on the evidence, and nobody calls the load balancer irrational for not predicting the crash.

<Callout type="exam" title="The slide’s wording: “Rational agent always performs right action”">
The slide says **"Rational agent always performs right action"**, where the right action is "the action that causes the agent to be most successful". Reproduce that sentence if a quiz asks for the lecture's definition.

It is imprecise because it confuses rationality with **omniscience**. An agent cannot always know which action *will* turn out best. It picks the action with the best **expected** outcome given its percepts and knowledge. For the full mark, add "expected" and the cargo-door example.
</Callout>

<Deeper kind="edge" title="Design the performance measure around the outcome, not the behaviour">

Russell and Norvig's warning: reward the vacuum for "amount of dirt sucked up" and a rational agent will suck up dirt, dump it back on the floor, and suck it up again. Measure **what you want in the environment** (clean floor, over time), not how you think the agent should behave. Any engineer who has watched a team game a metric ("tickets closed", "lines of code") has met this.

</Deeper>

## PEAS: specifying the task

Before designing an agent you specify its **task environment** with four headings: **P**erformance measure, **E**nvironment, **A**ctuators, **S**ensors. The lecture shows the textbook's table (R&N figure 2.5):

| Agent | Performance measure | Environment | Actuators | Sensors |
|---|---|---|---|---|
| Medical diagnosis system | Healthy patient, reduced costs | Patient, hospital, staff | Display of questions, tests, diagnoses, treatments, referrals | Keyboard entry of symptoms, findings, patient's answers |
| Satellite image analysis | Correct image categorisation | Downlink from orbiting satellite | Display of scene categorisation | Colour pixel arrays |
| Part-picking robot | Percentage of parts in correct bins | Conveyor belt with parts; bins | Jointed arm and hand | Camera, joint angle sensors |
| Refinery controller | Purity, yield, safety | Refinery, operators | Valves, pumps, heaters, displays | Temperature, pressure, chemical sensors |
| Interactive English tutor | Student's score on test | Set of students, testing agency | Display of exercises, suggestions, corrections | Keyboard entry |

<Deeper kind="beyond" title="Properties of task environments (R&N 2.3, not on the slides)">

Six yes-or-no questions classify any environment. The harder side of each pair is listed second.

| Property | Easy | Hard | The test |
|---|---|---|---|
| Observability | Fully observable | Partially observable | Can the sensors see everything relevant to the decision? |
| Agents | Single-agent | Multi-agent | Are other agents maximising their own measure, possibly against you? |
| Determinism | Deterministic | Stochastic / nondeterministic | Is the next state fully fixed by the current state and action? |
| Memory of episodes | Episodic | Sequential | Does the current decision affect future ones? |
| Change | Static | Dynamic (semi-dynamic if only the score changes with time) | Does the world change while the agent is deciding? |
| Values | Discrete | Continuous | Finite distinct states, percepts, actions? |

R&N's figure 2.6 examples:

| Environment | Observable | Agents | Deterministic | Episodic | Static | Discrete |
|---|---|---|---|---|---|---|
| Crossword puzzle | Fully | Single | Deterministic | Sequential | Static | Discrete |
| Chess with a clock | Fully | Multi | Deterministic | Sequential | Semi | Discrete |
| Poker | Partially | Multi | Stochastic | Sequential | Static | Discrete |
| Taxi driving | Partially | Multi | Stochastic | Sequential | Dynamic | Continuous |
| Medical diagnosis | Partially | Single | Stochastic | Sequential | Dynamic | Continuous |
| Image analysis | Fully | Single | Deterministic | Episodic | Semi | Continuous |
| Part-picking robot | Partially | Single | Stochastic | Episodic | Dynamic | Continuous |

The hardest case is the taxi: partially observable, multi-agent, stochastic, sequential, dynamic, continuous. That is why self-driving took decades.

</Deeper>

<Deeper kind="exam" title="Model answer: define agent, percept sequence, agent function and rational agent (5 marks)">

**Agent**: anything that perceives its environment through sensors and acts on it through actuators, for example a robot with cameras and motors. **Percept**: the agent's input at one instant. **Percept sequence**: the complete history of everything it has perceived. **Agent function**: a mapping from percept sequences to actions, F : P* → A. It is implemented by the **agent program**, which runs on the **architecture**; agent = architecture + program. **Rational agent**: for every percept sequence it selects the action expected to maximise its performance measure, given the percept sequence and its built-in knowledge. Rationality depends on the performance measure, the percept sequence, prior knowledge and the available actions. It is not omniscience: a rational agent maximises expected, not actual, performance.

</Deeper>
