Every servlet you write this semester sits at the end of the same pipe: a TCP connection carrying HTTP text. You know HTTP from other stacks, so this lesson moves fast and slows down only where the slides test something specific or get it wrong.

>

A TCP connection is not identified by the server's port. It is identified by all **four** numbers: source IP, source port, destination IP, destination port. The server listens on one port, 8080, but every accepted connection gets its own socket keyed by the full four-tuple. The client's port is **ephemeral**: the OS picks a free one from a high range for each new connection. The two browsers differ in that number, so there are two connections, two sockets, and Tomcat reads each independently.

## Sockets, IP addresses, ports

Slides 4 to 6 give the high-level view: client and server each have an `ip-address:port`, and a **socket** is the endpoint the program reads and writes. An **IP address** identifies a host on the network. A **port** identifies which program on that host gets the data. Tomcat asks the OS for a listening socket on port 8080 when it starts, and from then on the OS hands every incoming connection on 8080 to Tomcat.

| Range | Name | Who uses it |
|---|---|---|
| 0 to 1023 | well-known (system) ports | 22 SSH, 25 SMTP, 53 DNS, 80 HTTP, 443 HTTPS. Binding needs root on Linux. |
| 1024 to 49151 | registered ports | 5432 PostgreSQL, 8080 HTTP alternate (Tomcat's default), 3306 MySQL |
| 49152 to 65535 | dynamic or ephemeral | the client side of your connections (Linux actually uses 32768 to 60999) |

<Callout type="exam" title="Two port facts on slide 6">
The slide says: *"A computer system can have up to 65,535 virtual network ports"* and *"80 for HTTP, 23 for SMTP etc."*

- Port numbers are 16-bit, so 0 to 65535 exist: 65,536 values, with 0 reserved. They also exist **per transport protocol**, so TCP 53 and UDP 53 are different ports. If a quiz asks "how many ports", write 65,535 as the slide does and add "(numbered 0 to 65535, per protocol)".
- **SMTP is 25. Telnet is 23.** Never write "23 for SMTP", even if you have seen it on the slide.
</Callout>

## TCP/IP, the four-layer version

Slide 8 draws TCP/IP as **Application, Transport, Internet, Network Access**. That is the four-layer model from RFC 1122. In CNDC you use Kurose's five layers, which split Network Access into Link and Physical. Same stack, different granularity: HTTP lives in Application, TCP in Transport, IP in Internet, Ethernet or Wi-Fi in Network Access.

## What HTTP adds

The figure above is the whole protocol at the level this course needs. It has four properties:

1. **Text on a byte stream.** HTTP/1.1 is lines of ASCII over the TCP connection. You can type a request by hand with `nc localhost 8080`.
2. **Request, then response.** The client always speaks first. The server never sends anything that was not asked for.
3. **Stateless.** Each request carries everything the server needs. Remembering a logged-in user takes a cookie and a session, which comes later in the course.
4. **Status codes by class.** 2xx success, 3xx redirect, 4xx the client got something wrong (404 no such resource, 405 wrong method), 5xx the server broke (500 is an exception escaped your servlet).

<Callout type="key-idea" title="The container is the part you did not write">
In Node or Go your code owns the listening socket. Here Tomcat owns the socket, the thread pool, HTTP parsing and response writing. You write a class; Tomcat creates it and calls its methods. Tomcat is the **servlet container**, and the next three lessons are about the contract between it and your class.
</Callout>

<Deeper kind="beyond" title="See it yourself with curl and nc">

Once Tomcat is running (lesson "Set up, deploy, and log in"):

```bash
curl -v http://localhost:8080/
```

Lines starting with `>` are the request curl sent, lines with `<` are Tomcat's response headers. Or type the request yourself:

```bash
printf 'GET / HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' | nc localhost 8080
```

Then `ss -tnp | grep 8080` while a browser tab is loading shows the four-tuples from the Predict above.

"The client (browser) and the server (for example Tomcat) communicate over TCP/IP. The server listens on a known IP address and port, 8080 for Tomcat or 80 for HTTP in general. Over this connection the client sends an HTTP request made of a request line (method, path, version), headers, an empty line and an optional body. The server processes it, for example by running a servlet that may query a database, and returns an HTTP response made of a status line, headers, an empty line and the body, usually HTML.
