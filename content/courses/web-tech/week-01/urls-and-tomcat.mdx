A URL looks like an address for a file. On Tomcat it is really a set of instructions: which machine, which listening socket, which application, which servlet or file inside it. This lesson makes you read each part the way Tomcat reads it.

A **404**. The file is there, but everything under `WEB-INF` (and `META-INF`) is **private**: the container reads it to run the app and never sends it to a client. That is why your compiled classes and your database password in a config file are safe there, and why slide 31 splits a webapp into a "public area" and a "private area". <Callout type="exam" title="The &quot;App name&quot; label on slide 19">
The slide labels the first path segment **"App name"**. That is Tomcat's **context path** convention, not a property of URLs: to the URL standard (RFC 3986) the whole of `/7sport/index.htm` is just the path. On Tomcat, the first segment picks the webapp only when a webapp of that name is deployed. An app deployed as ROOT has an empty context path, so its URLs have no "app name" segment at all (`http://localhost:8080/index.jsp`).

On a quiz that uses the slide's diagram, label it "App name (context path)" so you match the slide and are still correct.

## Resolving the machine

Slide 21 lists three ways to name the machine. They differ in who translates the name:

| You type | Translated by | Leaves your laptop? |
|---|---|---|
| `www.7sport.net` | DNS: the resolver your network gives you (often your ISP's) | Yes, the DNS query and then the request |
| `localhost` | the hosts file (`/etc/hosts`, or `C:\Windows\System32\drivers\etc\hosts`) maps it to 127.0.0.1 | No |
| `127.0.0.1` | nothing; it is already an address, the **loopback** address | No, the OS loops it back to itself |

<QuickCheck

<Callout type="exam" title="Slide 28: &quot;its the web-apps directory on the server&quot;">
A WAR is **one** application. It is deployed **into** `webapps/`, where Tomcat expands `demo.war` into `webapps/demo/`, and the file name becomes the context path `/demo`. The `webapps` directory holds many applications. ## Public and private: write the paths

Slide 31's webapp: `index.html`, `index.jsp`, `tomcat.gif` are public and reachable at `/sample_webapp/index.html` and so on. `WEB-INF/classes/ServletX.class` is private: you reach the servlet through its **mapping** (`/hello-servlet`), never through its file path.

<Callout type="pitfall" title="localhost with no port">
Slides 32 and 51 write `http://localhost/sample_webapp/...` with no port, which means port 80. A freshly unzipped Tomcat listens on **8080**, so those exact URLs fail on your laptop. In your own work, use `http://localhost:8080/...`. On a quiz, follow whatever form the question uses.
</Callout>

<Deeper kind="edge" title="Where the context path actually comes from">

- `webapps/demo.war` or `webapps/demo/` gives `/demo`. The name is the context path.
- `webapps/ROOT/` or `ROOT.war` gives the empty context path: URLs start straight after the port.
- A `#` in the name becomes a `/`: `api#v2.war` is deployed at `/api/v2`.
- IntelliJ does not copy into webapps. It tells Tomcat to deploy from `target/` with the context path in the run configuration, which defaults to something like `/demo_war_exploded`. You will fix that in the setup lesson.

</Deeper>

<Deeper kind="exam" title="Model answer: describe the directory structure of a Java web application (5 marks)">

Draw slide 31's tree, then: "A web application has a root folder whose name is the context path. Files directly under the root (HTML, JSP, images, CSS) are the public area and are reachable by URL, for example /app/index.html. The WEB-INF folder is the private area and is never served to clients. It contains web.xml, the deployment descriptor that maps URLs to servlets; classes/, which holds the compiled servlet and helper classes; and lib/, which holds the jar libraries the application needs, such as a JDBC driver. For deployment the application is packaged as a WAR file and placed in Tomcat's webapps directory."

</Deeper>
