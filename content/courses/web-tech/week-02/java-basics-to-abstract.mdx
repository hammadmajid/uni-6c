## From Main.java to a running process

<WorkedExample title="The javac → bytecode → JVM pipeline (slides 3 to 13)">
  <Step label="The source">
    `MyProject/com/example/Main.java` starts with `package com.example;`. The package is a folder path: `com` is the parent folder, `example` the child, and the name is the company's domain reversed (`example.com` becomes `com.example`).
  </Step>
  <Step label="Compile" tryFirst="What file does javac produce, and what is inside it?">
    `javac com/example/Main.java` produces `com/example/Main.class`, containing **bytecode**: instructions for the JVM, not for your CPU. The same `.class` runs on any OS that has a JVM, which is the whole point.
  </Step>
  <Step label="Run" tryFirst="From which folder, with which name?">
    From `MyProject`, run `java com.example.Main Zubair`: the fully qualified class name, with no `.class` extension. The JVM loads the class, finds `main`, and passes `Zubair` in as `args[0]`.
  </Step>
  <Step label="Shortcut">
    Since Java 11, `java com/example/Main.java` compiles in memory and runs in one step. It is handy for a quick check; the quiz wants the two-step `javac`, then `java`.
  </Step>
</WorkedExample>

<Callout type="exam" title="Slides 6 to 8: javac Main.java, then java Main">
The slides compile and run with `javac Main.java` and `java Main`. For a class with `package com.example;` that does **not** run: from inside `com/example`, `java Main` fails with `Could not find or load main class Main (wrong name: com/example/Main)`. The working version is `java com.example.Main`, from the project root. If a question copies the slide's commands, reproduce them; if it asks how to run a packaged class, give the fully qualified name. Slide 2 also says the three statements must be "exactly as they appear", including `import java.lang.*;`. That import is harmless but redundant: every Java file imports `java.lang` implicitly, which is why `String` and `System` need no import.
</Callout>

Only a class with a `main` method can run on its own (slide 4). The signature is fixed:

| Part | Why it is there |
|---|---|
| `public` | The JVM calls it from outside the class. |
| `static` | Called before any object exists; there is no `this` yet. |
| `void` | Returns nothing. The exit code comes from how the JVM stops, not from a return value. |
| `main` | The name the launcher looks up. |
| `String[] args` | The command-line arguments, never null, possibly empty. |

Slide 17's diagram names the class loader subsystem, the **runtime data areas** and the execution engine. The runtime data areas are the part examiners ask about. Step through a three-line `main` and watch what lands where:

<JvmMemoryStepper />

<Callout type="key-idea" title="Two rules that answer most memory questions">
Every object is on the **heap**, shared by all threads. Every local variable, including a variable that holds a reference, is in a **stack frame** belonging to one thread. `Person p = new Person("Ali")` puts the object on the heap and the reference `p` on the stack. ## Objects, references and toString

`Person p = new Person();` then `System.out.println(p);` prints `com.example.Person@8efb846` (slides 19 and 20). To create an object you need a constructor and the `new` keyword, and what comes back is a reference to the object on the heap (slide 21). The value after `@` is the object's hash code in hex, **not** its memory address: `Object.toString()` returns the class name, `@`, then `Integer.toHexString(hashCode())`, and objects can move on the heap during garbage collection while that number stays fixed.

`println(p)` and `println(p.toString())` print the same thing, because `println` calls `toString()` on whatever it is given. Slide 27's exercise (solution on slide 28), printing your name instead of the "gibberish", is solved by overriding it:

```java
package com.example;

public class Person {
    @Override
    public String toString() {
        return "Zubair";
    }
}
```

Where does `toString` come from if `Person` never declares a parent? Slides 23 and 24: every class extends `java.lang.Object`, and if you do not write `extends`, the compiler writes `extends Object` for you. So a `Person` reference can be typed as `Person`, or as a parent type, all the way up to `Object`. That choice changes what compiles, but not what runs:

<RefTypeLab />

<Callout type="key-idea" title="Compile time looks at the reference, run time looks at the object">
javac allows a call only if the **declared type** has that method: `Object p = new Person()` cannot call `p.getName()`, which is slide 26's "you will not be able to call methods of the person class that are not in the Object class". At run time the JVM runs the **object's** version of the method. So `Object o = new Student("Ali")` then `println(o)` prints `Student: Ali`, using Student's override, even though `o` is declared as Object.
</Callout>

## Inheritance and super

Slides 29 to 38 start from `Student` and `Faculty` as copies of each other (a `name` field, a constructor, a getter and a setter), then move the shared part into a parent:

```java
public class Person {
    private String name;

    public Person(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }
}

public class Student extends Person {
    Student(String name) {
        super(name);   // runs Person(String) first
    }
}
```

`name` is `private` to Person, so Student cannot touch it directly; it gets there only through `super(name)` and later through `getName()`. `super(...)` calls the parent's constructor, so the parent's part of the object is built before the child's.

<Deeper kind="edge" title="Constructor order, and super() no longer has to come first">

Every constructor starts by running its parent's, all the way up to Object, so with `Person()` printing `Person()` and `Student()` printing `Student()`, `new Student()` prints `Person()` first, then `Student()`.

The textbook rule "`super(...)` must be the first statement" was relaxed in **Java 25** (JEP 513, flexible constructor bodies): code that does not touch `this`, such as validating an argument, may now come before `super(...)`. Your JDK 26 compiles it, and older JDKs reject it. For the quiz, "super must be the first statement" is still the expected answer unless the question says otherwise.

</Deeper>

## Abstract classes

Slide 39 marks `Person` as `abstract`, and `new Person("Zubair")` stops compiling: `Person is abstract; cannot be instantiated`. That is fine, because nobody is just a Person; everyone is a Student or a Faculty. Slides 41 to 47 then build the classic example, `Employee`, whose `earnings()` has no sensible body in the parent.

<Predict
  id="jb-abstract-predict"
  prompt="Employee declares public abstract double earnings(); with no body. SalariedEmployee extends Employee but you forget to write earnings() in it. Does SalariedEmployee compile? Would it compile if you also marked SalariedEmployee abstract?"
  answer="No: 'SalariedEmployee is not abstract and does not override abstract method earnings() in Employee'. Yes, if SalariedEmployee is itself abstract; then the obligation passes down to its first concrete subclass."
>

The first **concrete** (non-abstract) class in the chain must implement every inherited abstract method. javac's words: `SalariedEmployee is not abstract and does not override abstract method earnings() in Employee`. An abstract subclass can leave it unimplemented and pass the job down.

</Predict>

| Rule | What javac says if you break it |
|---|---|
| An abstract method has no body, and must say `abstract` | `missing a method body, or should be declared abstract` |
| A class with even one abstract method must be declared abstract | `is not abstract and does not override abstract method` |
| An abstract class cannot be instantiated with `new` | `is abstract; cannot be instantiated` |
| A concrete subclass must override every abstract method | `is not abstract and does not override abstract method` |
| An abstract class **can** have fields, constructors and concrete methods | (allowed: Person keeps `name`, its constructor and `getName`) |
| An abstract class **need not** have any abstract method | (allowed: slide 39's Person has none) |

Here is the Employee family with the slides' bugs fixed, plus the two exercises from slides 49 and 50 (an array of Employee and a List of Employee), compiled and run:

```java
public abstract class Employee {
    private String name;

    public Employee(String name) {      // needed: the children call super(name)
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public abstract double earnings();  // no body
}

public class SalariedEmployee extends Employee {
    private double weeklySalary;

    public SalariedEmployee(String name, double weeklySalary) {
        super(name);
        this.weeklySalary = weeklySalary;
    }

    @Override
    public double earnings() {
        return weeklySalary;
    }
}

public class HourlyEmployee extends Employee {
    private double rate;   // per hour
    private double hours;  // this week

    public HourlyEmployee(String name, double rate, double hours) {
        super(name);
        this.rate = rate;
        this.hours = hours;
    }

    @Override
    public double earnings() {
        return rate * hours;
    }
}

// in main:
Employee[] staff = new Employee[2];                 // an array of references: allowed
staff[0] = new SalariedEmployee("Zubair", 50000);
staff[1] = new HourlyEmployee("Ali", 1500, 20);

List<Employee> payroll = new ArrayList<>();         // java.util.List, java.util.ArrayList
payroll.add(staff[0]);
payroll.add(staff[1]);

for (Employee e : payroll) {
    System.out.println(e.getName() + " earns " + e.earnings());
}
// Zubair earns 50000.0
// Ali earns 30000.0
```

`new Employee[2]` creates an **array of two empty references**, not two Employee objects, which is why it is allowed for an abstract type (slide 48: "abstract can still behave like types"). The loop calls `earnings()` through an Employee reference, and each object runs its own version: the same dispatch as `toString` in the lab.

<Deeper kind="exam" title="Model answer: what is an abstract class? Give an example. (4 marks)">

An abstract class is a class declared with the `abstract` keyword that **cannot be instantiated**. It exists to be extended: it holds the fields and methods its subclasses share, and can declare **abstract methods** (no body) that every concrete subclass is forced to implement. A class with even one abstract method must itself be declared abstract.

Example: `Employee` is abstract, with a `name` field, `getName()`, and `public abstract double earnings();`. `SalariedEmployee` returns its weekly salary from `earnings()`, and `HourlyEmployee` returns rate × hours. `new Employee()` is a compile error, but `Employee[] staff` can hold both kinds, and `staff[i].earnings()` runs each object's own version.

The marks: the definition with "cannot be instantiated" (1), abstract methods have no body and must be implemented by subclasses (1), the example with the abstract method (1), and a subclass implementing it (1).

</Deeper>

<Deeper kind="beyond" title="Java 25's instance main methods">

Since Java 25 (JEP 512), a file containing just `void main()` with `IO.println("Hi");` inside is a complete program: no class declaration, no `static`, no `String[] args`. It runs on your JDK 26. The quiz and the deck use the classic `public static void main(String[] args)`, and so does every framework you will meet, but it explains the shorter programs you may see in newer tutorials.

</Deeper>
