You have shipped plenty of working software without ever drawing a process diagram. So the honest question is: what does "engineering" add that skilled coding does not? The lecture's answer is about **scale, cost and change**, the three forces that break the lone-hacker approach.

The weekend app and the bank system might compute the same thing. What differs is everything *around* the code: coordination across many people, the cost of a defect, and the number of years and hands the system has to survive. ## The definition to memorise

The IEEE definition, straight off the slide:

> Software engineering is **the application of a systematic, disciplined, quantifiable approach** to the development, operation and maintenance of software; that is, the application of engineering to software.

Three load-bearing words: **systematic** (a repeatable method, not ad hoc), **disciplined** (you follow it even when it is inconvenient), **quantifiable** (you measure, so you can tell whether it is working). Notice it covers **operation and maintenance**, not just development. The build is a slice of the life; the long tail is running and changing it.

## Why you cannot just scale up hacking

The lecture lists five forces that make an engineering process necessary. Read them as failure modes of the no-process approach:

- **Large software**: building a wall is not building a house. Past a certain size, informal methods collapse under their own coordination cost.
- **Scalability**: without engineering foundations, growing a system is harder than rewriting it, so nothing compounds.
- **Cost**: hardware got cheap through disciplined manufacturing; software stays expensive precisely when the process is undisciplined.
- **Dynamic nature**: requirements and environments keep shifting, so the system needs a controlled way to absorb change (the maintainability point from the last lesson).
- **Quality management**: a better process is the only reliable route to a better product. You cannot inspect quality in at the end.

## Engineering is a layered technology

The slide pictures software engineering as a stack. Each layer rests on the one below:

<SeLayeredTechnology />

The bedrock is a **quality focus**: without a culture that cares about quality, the layers above are theatre. On it sits the **process**, the framework that holds everything together and defines what gets done when. **Methods** provide the technical how-to for each activity (how to gather requirements, design, test). **Tools** (your IDE, Git, CI, profilers) automate and support the methods. Pull out the process layer and your tools are just fast ways to make a mess.

<Callout type="pitfall">

The tempting mistake is to buy tools and call it engineering. Tools are the top, thinnest layer. A team with the best CI pipeline and no process still ships chaos, faster. The exam likes this ordering question: quality focus, then process, then methods, then tools, bottom to top.

</Callout>

## Different software, different build

The application type shapes how you should build. The lecture's domains are not just labels; each implies a different method emphasis:

| Application type | What it is | Where the engineering weight goes |
|---|---|---|
| System software | OSes, drivers, compilers | Correctness, performance, low-level rigour |
| Application software | Business and productivity apps | Requirements fit, usability |
| Engineering/scientific | Simulations, number crunching | Numerical accuracy, validation against reality |
| Embedded software | Firmware inside devices | Real-time limits, reliability, tiny resources |
| Product-line software | One codebase, many configured products | Reuse, variability management |
| Web applications | Networked, browser-delivered systems | Security, scale, evolution speed |
| AI software | Learning and reasoning systems | Data quality, evaluation, unpredictability |

You feel this already: you would never test a payments backend the way you test a throwaway data script. Same discipline, different dials.
