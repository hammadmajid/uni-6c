You ship code for a living, so "what is software" sounds like a question you answered in 2019. This first lesson is about the gap between the code you push and the thing the customer actually bought, because that gap is the whole reason software engineering exists.

## Software is three things, not one

The IEEE-style definition on the slide has three parts:

1. **Instructions** (the programs) that when executed provide the desired features, function and performance.
2. **Data structures** that let the programs manipulate information adequately.
3. **Documentation** that describes the operation and use of the programs.

Miss any one and you do not have a product. A backend with no schema is not going to manipulate anything; a service with no runbook is not something an ops team can operate at 3am. You already know this in your bones as "code is the easy part".

## Software does not wear out, but it does rot

A car door has a fatigue life; hinge it a million times and it fails. Software has no such physical failure mode: the same bits run the same way on day 3000 as on day 1. The slide's point is that software is **developed or engineered, not manufactured** in the classical sense, and it **does not wear out**.

So why does old software feel broken? Not wear, but **change**. Every bug fix and feature edit perturbs the system, and each perturbation can introduce new faults. The idealised reliability curve should flatten forever; the real curve creeps upward with every change, because the world around the code (the OS, the libraries, the business rules) moves and the code is dragged after it. That is exactly what the lecture calls **legacy software**: systems that must be adapted, enhanced, extended or re-architected to keep working in a world that changed underneath them.

<Callout type="key-idea">

Hardware fails from wear; software "fails" from change. This flips your maintenance intuition: the risky moment for a running system is not old age, it is the next edit. That is why so much of this course is about controlling change.

</Callout>

## Two ways to slice the software zoo

The lecture classifies software twice. First by **how well the problem is understood** (Lehman's S/P/E types):

| Type | Meaning | Example |
|---|---|---|
| **S-type** (static) | Fully specifiable; the problem and its solution are exactly known and do not change | A calculator |
| **P-type** (practical) | Specifiable, but the solution is not obvious; you know the end result, not the route | A chess or sketch program |
| **E-type** (embedded) | Models a real-world process and becomes part of that world, so it must evolve with it | Air-traffic control, online trading |

Then by **application domain**: system software, application software, engineering/scientific software, embedded software, product-line software, web applications, and AI software. These are not exclusive; a modern product is usually several at once.

## What makes software good

A program that "works" can still be bad software. Sommerville names **four essential attributes** of good software, and these are what quizzes ask you to recall:

<SeQualityAttributes />

- **Maintainability**: it can be changed cheaply as needs evolve. This is the master attribute, because change is the norm (see above).
- **Dependability and security**: it does not fail dangerously, does not lose or leak data, and resists attack.
- **Efficiency**: it does not waste CPU, memory, network or power.
- **Acceptability**: the intended users understand it, can use it, and it is compatible with the systems they already run.

Notice all four are **non-functional**: they say nothing about *what* the program computes, only about how well it lives in the world. As a backend engineer you already trade these off every sprint (a cache is efficiency bought with a maintainability cost). The exam just wants the names.

<Callout type="exam">

The instructor's slides do not use Sommerville's four-attribute list. They group quality as **Operational** (usability, efficiency, correctness, dependability, security, safety), **Transitional** (portability, interoperability, reusability, adaptability) and **Maintenance** (modularity, maintainability, flexibility, scalability). If a question says "characteristics of good software", give the slide's three groups; you can add Sommerville's four essentials as the modern summary. Both are examinable phrasings of the same idea, so write the slide's for the marks and keep the four essentials as your backbone.

</Callout>
