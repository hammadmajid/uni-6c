Every team has a way of turning an idea into running software, even if nobody wrote it down. The lecture's word for that way is the **software process**. This lesson names the four activities every process is built from, so that next week the models (waterfall, incremental, reuse) are just different *orderings* of the same four.

## The software process

The slide defines a **software process** as a **road map that helps you create software**: the way we produce software, giving **stability and control**. Its other job is to define **work products** (also called deliverables): the programs, documents and data produced as a consequence of the engineering activities.

That phrase "documents and data", not just programs, is the same point as week 1: the output of a process is software, not merely code. A design document, a test report and a schema are all work products, and a process that produces none of them produces nothing another team can trust.

## The four generic activities

Sommerville reduces every process to **four fundamental activities**:

<SeProcessActivities />

- **Specification**: define what the software must do, and the constraints on it. Its main work product is a requirements document.
- **Development (design and implementation)**: design the architecture, then write the code. Work products: design documents and source code.
- **Validation**: check that the software does what the customer wanted. Work products: test plans, test results.
- **Evolution**: change the software in response to changing needs. This is not an afterthought; it is where most of a long-lived system's life and cost sit.

The arrows show the naive left-to-right order, but the loop matters more: **evolution feeds new requirements back into specification**. A running system is never "done"; it is between changes.

## Mapping the slide's SDLC onto the four

The instructor's SDLC slide lists **seven** phases. They are not a different theory; they are a finer-grained cut of the same four activities. Line them up:

| Slide's SDLC phase | Generic activity | Role named on the slide |
|---|---|---|
| Requirement gathering | Specification | Business analyst |
| Requirement analysis | Specification | Business analyst |
| Design | Development | System architect |
| Development / coding | Development | Developer |
| Testing | Validation | Tester |
| Deployment | Evolution (release) | All team |
| Maintenance | Evolution | Support / technical team |

The slide's requirements-gathering questions are worth keeping, because exams reuse them: *who will use the system, how will they use it, what data goes in, what data comes out*. And the analysis phase produces the **Software Requirements Specification (SRS)**, the document that guides design, development and testing.

<Callout type="exam">

Two SDLC facts the slide states that quizzes love: (1) the requirements-analysis phase produces the **SRS**, which serves as the guideline for design, development and testing; (2) the **design** phase produces a **Design Document Specification (DDS)** that specifies hardware, system requirements and the overall architecture. If asked "what is the output of the analysis/design phase", give the SRS/DDS by name.

</Callout>

## Work products are the currency

Because the process is defined by its deliverables, "which activity am I in" is usually answered by "which work product am I producing". A quick map:

| Work product | Activity |
|---|---|
| Requirements document / SRS | Specification |
| Architecture and design (DDS) | Development |
| Source code | Development |
| Test plan and test report | Validation |
| Release notes, patches | Evolution |

<Deeper kind="beyond" title="Where DevOps fits">

The four activities predate continuous delivery, but they still hold. A modern CI/CD pipeline does not remove specification, development, validation and evolution; it *compresses the loop* so that all four happen for a tiny slice of change, many times a day. When you open a PR (specification of a small change), implement it (development), let CI run the tests (validation) and merge and deploy (evolution, then straight back to the next change), you are running the same four activities on a very tight cycle. Next week's incremental model is the textbook name for that instinct.

</Deeper>
